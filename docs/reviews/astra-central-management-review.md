# 중앙 AI PMS 목적 및 증거 모델 독립 검토

검토일: 2026-10-01. 검토자: `/root/astra_central_management_review`. 판정: **inadequate — 최신 전체 목적에는 미달, 기존 구현은 재사용 가능한 부분 기반**.

이 판정은 사용자 최신 설명을 전달받은 독립 검토입니다. 코드와 문서를 읽고 반환 검증기의 한 가지 반례만 메모리에서 실행했습니다. 새 제품 구현·하네스 변경·외부 통신·배포를 하지 않았으며 공개 서비스의 현재 동작을 재검증하지 않았습니다. 이전 배포 및 브라우저 검증은 저장된 당시 기록으로만 취급했습니다.

## 목적 판단

관리 대상은 여러 사람의 프로젝트 목록을 넘어 **목표를 맡기고, 수행과 근거를 추적하며, 막힌 일을 해결하고 공통 Agent 작업 방식을 개선하는 운영 과정**입니다. 회사는 성과 목표 또는 구체 작업을 맡길 수 있고 개인은 자신의 환경과 방법으로 수행합니다. 개인 프로젝트도 같은 관측·개선 체계에서 다룹니다. 모든 개인 목표를 하나의 회사 목표 아래 강제로 넣을 필요는 없습니다.

`PRODUCT-INTENT.md:고정할 제품 목적`과 `PRODUCT-CLARIFICATION.md:대시보드 방향`은 다수 사용자·세션·문서·검증 연결에는 맞지만 회사 목표 위임, 목표 달성 근거, 공통 하네스 개선 운영까지 구체화하지 않았습니다. 최신 설명을 원문 출처와 함께 보충해야 합니다. 이전 범위의 인수 기록을 소급 수정하거나 무효화할 이유는 없습니다. 이전 검사는 해당 범위의 근거이지 새 목적의 인수 근거가 아닙니다.

## 현재 가능한 것과 없는 것

| 관리자 질문 | 현재 근거 | 판정과 빠진 기능 |
|---|---|---|

| 무엇을 어떤 조건으로 통과했는가? | `CRITERION_KEYS`, `runs`, `criterion_signature`, `build_model:state` | 명령·범위·기대 종료 코드·대상 revision·가져온 결과를 표시합니다. 기준의 이유/요구사항별 커버리지/실제 runner/환경/검사 파일 버전/시도 ID가 없습니다. |
| 왜 막혔고 누구의 도움이 필요한가? | 실패한 검사와 연결/수집 경고 | 실패 상태는 보이나 차단 원인·시도한 해결·다음 조치·지원 담당자·해결 후 재검증 연결은 없습니다. |

기존 중앙 집계, 명시적 프로젝트 연결, 원본 근거, 문서 버전, 작업/단계/프로젝트 검사 구분, 현재 revision 재검증, MCP 출처 표시, 파일 가져오기는 유지할 가치가 있습니다. 자동 PC 수집 연기는 위 기록 모델과 화면 개선을 막지 않습니다.

## JSON 템플릿과 설명은 실제로 어디에 있는가

- `specs/ai-pms-dashboard/README.md:입력 작성`: catalog/store/snapshot 차이와 검사 의미를 설명합니다.
- `specs/ai-pms-dashboard/sample/catalog.json`: 프로젝트·문서·검사·결과를 넣은 합성 입력 예시입니다. 빈 업무용 작성 템플릿이나 통합 수집 명세는 아닙니다.
- `specs/ai-pms-dashboard/sample/README.md`: 합성 시나리오와 criterion fingerprint 생성법입니다.
- `specs/ai-pms-dashboard/portfolio.py:validate_catalog`: 현재 catalog의 실제 허용 필드 계약입니다. 알려지지 않은 필드를 추가하면 거부합니다. 따라서 새 의미를 임의 JSON 키로 넣어 기존 제품이 처리할 수 있다고 안내하면 안 됩니다.
- `~/.claude/harness/activity/logger.py:LINKS/DATA/record_event/hook_event` 및 같은 폴더 `README.md`: 로컬 이벤트 허용 필드, 명시적 기록, MCP v2 계약입니다.
- `~/.agents/skills/handoff/{plan,packet,result}.schema.json`: 계획의 원문 요구사항, 작업 패킷, 반환 검사 요약 계약입니다. 중앙 catalog와 자동 연결하는 어댑터는 위 대시보드 코드에 없습니다.
- `~/.claude/harness/build/current_content.py:PAGES['ai-pms']`: 공개 안내 정본에는 MCP 예시와 관측/선언 경계가 있지만 목표 위임부터 테스트 계획·개선 조치까지 한 번에 따라 작성할 수 있는 가이드가 없습니다.

사용자가 찾는 설명은 여러 곳에 흩어져 있고, 질문한 전체 정보를 수용하는 통합 템플릿 자체가 아직 없습니다. 다음 안내는 **누가/언제/무엇을 기록하는지, 자동 관측인지 명시 기록인지, 원문 위치, 필수/선택, 미관측 의미, 실제 예제**를 한 문서에 연결해야 합니다. UI 가져오기가 받는 것은 raw catalog가 아니라 정규화 snapshot이라는 차이도 첫 안내에서 밝혀야 합니다.

## 테스트 계획과 통과 로그가 부족한 이유

1. `logger.py:hook_event`는 일반 도구 이벤트에서 `data={}`를 유지합니다. 도구 이름·상관 ID·시각은 남겨도 일반 Bash 명령/출력/테스트 설계 이유를 기록하지 않습니다. `PostToolUse`를 검사 통과로 변환하지 않습니다.
2. `logger.py:DATA`의 `check.recorded`는 `summary/status/environment`, 링크는 check/artifact/version 등을 받습니다. 테스트 계획 ID/버전/요구사항/시도/실제 실행 영수증을 표현하는 계약이 없습니다.
3. `portfolio.py:CRITERION_KEYS`는 `id,label,scope,target_id,command,expected_exit_code`뿐입니다. 기준을 왜 만들었는지, 어떤 요구사항을 얼마나 확인하는지, 어떤 테스트 파일이 실행되는지는 기준 해시에 포함되지 않습니다.
4. `result.schema.json:acceptance_run`은 `command/exit_code/output_tail` 요약 한 건입니다. 실행 시각, runner/환경, revision digest, 실패부터 통과까지 여러 시도는 필수가 아닙니다. `plan.schema.json:intent_guard`는 원문 요구사항을 작업에 연결하나 테스트 케이스별 커버리지와 동등하지 않습니다.
5. `session_gate.py:scan`은 관측한 마지막 코드 편집 이후 인식 가능한 검증 도구 결과가 있는지를 확인합니다. 프로젝트 목표에 충분한 검사를 설계했는지 판단하거나 중앙에 프로젝트 인수 영수증을 발급하지 않습니다.
6. Kit는 설치 절차와 점검 방법을 제공하지만 모든 사용자 환경의 설치·실제 적용·버전이 동일하다는 증거는 아닙니다. `current_content.py:SCENES['ko']`도 파일/검사와 실제 앱 호출의 차이를 명시합니다.

따라서 로그를 일부러 누락했다기보다 **현재 계약이 실행 흔적과 최종 요약 중심이고, 테스트 설계·개정·실패 분석·수정·재검증의 기록 책임과 연결이 정의되지 않은 상태**입니다.

## 구체적인 기존 사례

**합성 Alice:** `sample/catalog.json:projects[id=alice-recall].runs`는 같은 v1에서 04:00 exit 1, 08:00 exit 0을 담습니다. 각 evidence는 명령을 실행하지 않은 합성 기록이라고 명시합니다. 현재 관리자는 실패 뒤 통과한 시간을 읽지만 무엇이 실패했고 무엇을 고쳐 통과했는지 알 수 없습니다. 이 예시를 실사용자 개선 루프 증거로 제시하면 안 됩니다.

**합성 Bob/Carol:** Bob은 단계 검사를 통과하고 전체 검사에 실패합니다. Carol은 v1 통과 후 v2 결과가 없어 재검증으로 표시됩니다. 이 범위 구분은 적절합니다. 다만 revision은 입력자가 적는 식별값이며 실제 코드 변경 감지는 수동입니다. 기준 정의가 바뀌면 예전 완료 이력은 별도 snapshot 보존이 필요합니다(`README.md:입력 작성`).

**실제 작업 반환 기록:** `specs/ai-pms-dashboard/data-model-result.json:acceptance_run`에는 `python3 specs/ai-pms-dashboard/test_portfolio.py`, exit 0, `Ran 16 tests ... OK`가 있습니다. `done_when_check`에는 revision freshness, changed signature, future/conflict, wrong scope, source identity 반례가 나열됩니다. 이는 해당 기능 검사의 저장된 실행 요약입니다. 어떤 원문 요구사항 때문에 각 반례가 생겼는지, 첫 실패/수정/재실행의 순서, 실행 대상 content hash는 그 반환 기록에 없습니다.

**검증기 반례:** 현재 `validate.py:check_result`는 반환 `acceptance_run.command`와 패킷의 `acceptance.command`가 같은지 검사하지 않습니다. 위 결과 JSON을 메모리에 읽어 command만 `echo unrelated`로 바꿔 검사했을 때 `errors=[]`, `warnings=[]`였습니다. 파일은 바꾸지 않았습니다. 이 결과는 반환 계약 검사가 실제 올바른 검사 실행을 보증하지 못함을 보여줍니다. 모든 기존 통과가 거짓이라는 뜻은 아닙니다.

**공개 릴리스:** `specs/ai-pms-connectivity/release-proof.json`에는 `evidence_mode=synthetic`, `live_user_delivery_verified=false`, `automatic_collection_deferred=true`가 명시돼 있습니다. 공개 샘플 배포와 저장된 브라우저 검증을 회사 목표 관리 및 실제 여러 사용자 운영 완료로 확대할 근거가 없습니다.

## 필요한 최소 증거 연결

제안이며 아직 구현된 계약이 아닙니다. 기존 이벤트를 전부 확장하기보다 **버전 있는 로컬 프로젝트 기록과 실행 영수증을 연결하고 snapshot으로 가져오는 방식**부터 만들면 됩니다.

`목표/위임 버전 → 원문 요구사항 → 계획 버전 → 테스트 계획/기준 버전 → 실행 시도 → 대상 산출물 버전 → 결과 → 조치/재검증`

| 기록 | 최소 정보와 작성 책임 |
|---|---|
| 목표와 위임 | 조직 목표 연결은 선택. 위임자/수임자, 성과형 또는 작업형, 원문 출처, 목표/제약/성공 조건, 변경 이유와 확정 주체. 개인 목표를 강제로 회사 목표에 연결하지 않습니다. |
| 계획·기준 생성/개정 | plan/criterion ID와 version, 이전 버전, 작성자·시각, 요구사항 IDs, 이 검사를 고른 이유, 확인할 사실/기대 결과, 범위, 제외·미검증 항목, 테스트 파일/content digest. Agent가 작업하면서 기록하고 해석은 원문과 구분합니다. |
| 실행 시도 | run ID, plan/criterion version, command/안전한 실행 위치 참조, start/end, runner ID, 환경/도구 버전, 입력/테스트/산출물 digest, 종료 코드, 결과 요약과 보관된 출력 참조. 신뢰 가능한 로컬 runner가 직접 생성합니다. |
| 결과 판정 | 설정된 기준 충족 여부, 요구사항별 근거/미검증/제외, 대상 revision, 판정 주체, 예외·waiver와 이유. 명령 종료 성공만으로 의미적 커버리지를 완성으로 만들지 않습니다. |
| 막힘과 개선 | blocked ID, 시작/해제, 원인 가설/확정 구분, 관련 실패 run, 이미 시도한 수정, 도움 요청/담당자, 다음 조치, 해결 run. 개선은 사용한 rule/skill/hook/MCP 버전과 변경 전후 근거를 연결합니다. |

Git commit만으로 dirty 파일을 포함한 실행 대상이 확정되지는 않습니다. 최소한 실행에 쓰인 소스·테스트·설정 manifest의 digest를 보관해야 합니다. 해시는 대조값이지 기록 작성자의 진실성 보증이 아닙니다. 기준 변경은 덮어쓰지 않고 이전 버전을 남겨 당시 통과 조건과 현재 미충족 조건을 함께 보여야 합니다.

증거는 한 줄짜리 점수보다 서로 다른 축으로 표시합니다. **작성 출처**(agent-declared/hook-observed/runner-produced/reviewer-confirmed), **검사 범위**(task/phase/project/outcome), **검증 환경**(unit/mock/local integration/browser/live provider/production), **대상 최신성**(current/stale/unknown)을 구분합니다. 로컬 runner 통과가 실제 provider 검증보다 항상 강하거나 약한 단일 서열은 아닙니다. 각각 확인한 질문이 다릅니다.

## 중앙에서 보여야 하는 판단과 행동

- 회사 목표에는 연결된 위임, 담당자, 성과 기준, 산출물 인수와 성과 관측을 나란히 보입니다. 예를 들어 처리시간 단축 목표에 대해 앱의 기능 검사가 통과해도 실제 업무 소요시간 근거가 없으면 **산출물 기준 충족 / 성과 미관측**입니다.
- 개인 프로젝트에도 목표/기준 누락, 기준 변경 후 미검증, 같은 실패 반복, 외부 접근 차단, 도움이 필요한 결정이 드러나야 합니다. 단순 무활동을 blocked로 단정하지 않습니다.
- 반복 실패 알림에는 실패 서명, 관련 버전, 마지막 수정, 다음 조치, 담당자를 붙입니다. 관리자는 요구사항을 정리하거나 접근 권한 문제를 해결하거나 적합한 스킬/검사를 보완할 수 있어야 합니다.
- 하네스 현황은 배포된 Kit 버전, 로컬 설치 선언, 실제 관측한 hook 발동, 검사 실행 여부를 나누어 보여야 합니다. 스킬 미사용만으로 오사용을 판정하지 말고 작업에 적용할 이유와 예외를 봅니다.
- 개선 항목은 “가설 → 변경 → 제한된 재실행 → 효과 근거 → 적용/보류”로 닫습니다. MCP 호출 수·세션 수·문서 수·테스트 수를 생산성 또는 개인 성과 점수로 만들지 않습니다. 사용량 증가는 문제의 복잡성이나 도구 오류 때문일 수도 있습니다.

권장 예시는 “Alice가 같은 실패를 두 번 겪었고, 원인은 MCP 권한 부족으로 확인됨 → 관리자에게 자원 접근 검토 할당 → 새 연결로 동일 기준 재실행 → 통과 → 해당 환경 설정 가이드 개선”입니다. 이는 **제안 시나리오**이며 기존 합성 Alice 로그에서 관측한 사실이 아닙니다.

## 다음으로 쓸 수 있는 최소 범위와 인수

### Graphify 자동 생성에 대한 후속 검토

사용자 후속 설명은 “필수라면 자동 생성하고 로깅에 도움이 되는지 보자”는 조건부 방향입니다. **Graphify는 목표·테스트 증거 기록의 필수 선행조건이 아닙니다.** 이번 대상 루트에는 `graphify-out/graph.json`이 없었고 지정된 소스·계약 직접 확인으로 위 판단이 가능했습니다. 별도 추출이나 훅 설치는 하지 않았습니다.

코드 의존관계를 조사하거나 변경된 코드와 연결된 테스트 후보를 찾는 데에는 선택적 AST 그래프가 도움이 됩니다. 기존 그래프를 재사용하고, 반복적인 넓은 탐색 비용이나 변경 영향 추적 필요가 확인될 때 로컬 `--code-only --no-cluster` 추출을 추가하는 편이 타당합니다. 매 도구 실행 전에 전체 그래프를 다시 만들거나 그래프 실패로 작업을 막는 것은 이 목적에 필요하지 않습니다.

자동화한다면 프로젝트별 opt-in으로 관련 파일 변경을 모아서 갱신하거나 commit 후 갱신하는 방식이 후보입니다. commit 후 방식은 미커밋 작업을 놓치므로 `source_revision`에 dirty 상태와 대상 파일 manifest digest를 포함하고 freshness를 표시해야 합니다. 기록할 최소 정보는 graph artifact ID/version, generator/version, 추출 모드, 범위, source revision/digest, generated_at, 생성 성공/실패, 관련 실행/event 참조입니다. 대시보드는 오래된 그래프와 생성 실패를 미관측으로 남깁니다.

AST의 import/call/정의 관계는 **구조상 연결 근거**입니다. 실제 런타임 호출, 동적 의존성 전체, 테스트 실행 커버리지, 사용자 요구사항의 의미 충족을 증명하지 않습니다. 따라서 “연결된 테스트 후보”와 “실제로 요구사항을 검증한 실행”을 별도 표시해야 합니다. 그래프는 원문 요구사항→기준→runner 실행→산출물 증거 사슬의 보조 산출물입니다. 홈 전체 인덱싱, 외부 semantic/API 추출, 전역 훅 자동 설치는 이 검토의 제안에 포함하지 않습니다.

1. 최신 사용자 목적을 원문과 연결하고 기록 안내·빈 템플릿·작은 정상/누락 예시를 함께 설계합니다. 기존 handoff 문서를 재작성하게 하기보다 명시적으로 선택한 로컬 plan/result를 읽는 어댑터로 재사용합니다. 없는 이유·이력은 자동 창작하지 않고 미관측으로 둡니다.
2. 조직 목표 연결은 선택인 위임 기록과 버전 있는 테스트 계획/실행 영수증/막힘·개선 기록을 로컬 파일로 구현합니다. 기존 중앙 snapshot 가져오기에서 탐색하도록 연결합니다. 신규 API·DB·전역 훅·배포는 이번 단계의 필수조건이 아닙니다.
3. 두 참여자 출처를 가진 **회사 성과형 위임 1개, 구체 작업형 위임 1개, 독립 개인 프로젝트 1개**를 사용해 필터·목표→위임→요구사항→기준→실행→수정→재검증을 확인합니다. 합성 시연과 실제 로컬 실행은 명시적으로 구분합니다.
4. 실제 로컬 검사 한 건에서 실패 → 수정 → 통과를 runner가 기록하고, 이후 산출물 변경/기준 개정이 재검증 상태를 만드는지 확인합니다. 이전 통과 이력을 보존하고 다른 command의 영수증·다른 artifact hash·다른 criterion version이 최신 완료로 채택되지 않아야 합니다.
5. 중앙 사용자가 “어떤 목표가 왜 막혔고 누구에게 무엇을 요청할지”, “어떤 기준으로 통과했고 무엇은 아직 확인하지 않았는지”, “어떤 하네스 변경을 왜 제안하고 어떻게 확인할지”를 원본 근거까지 찾아 답할 수 있어야 합니다.

이 범위의 결과 명칭은 **로컬 근거를 가져오는 목표·검증·개선 관리 흐름**이 적절합니다. 자동 PC 수집/운영 인증/실사용자 전송은 deferred로 유지합니다. 제안한 로컬 계약은 검토 가능한 설계이며 현행 계약을 이미 변경했다는 뜻이 아닙니다. 회사 성과 데이터 연동, 신규 외부 API·DB·배포는 필요한 시점에 구체 범위 승인을 따릅니다.
