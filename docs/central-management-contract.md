# 중앙 관리 기록 계약 — 목적과 구현 경계

2026-10-02 사용자 설명과 독립 검토를 반영했습니다. 목표·위임·계획·테스트 시도·막힘·Kit 개선·선택 그래프를 v3 catalog/snapshot과 로컬 기록기로 구현했습니다. 기존 훅 JSONL 계약을 바꾸지 않고 별도 관리 기록을 연결합니다. 정확한 지원 필드와 CLI는 [JSON 안내](json-contracts.md), [구현 명세](../specs/ai-pms-management/spec.md), Kit activity/README.md에 있습니다. 아래 내용 중 회사 업무 성과 수집·외부 신뢰 서명·다중 PC 자동 전달은 구현 범위가 아닙니다.

## 관리 목적과 기록 연결

회사 또는 개인 목표 → 선택적인 위임 → 요구사항·계획 → 테스트 계획 → 실행·실패·수정·재검증 → 산출물 → 설정된 완료 조건 충족을 연결합니다. 회사 목표를 달성했는지는 기술 검사와 별도로 업무 결과 근거를 확인합니다. 개인 프로젝트에는 회사나 위임을 요구하지 않습니다.

| 기록 | 최소 필요한 내용 | 기록 책임 |
|---|---|---|
| 목표·위임 | 목표 ID/버전, 원문 출처, 회사/개인 구분, 상위 목표, 위임자·담당자, 결과 위임/작업 지시 구분, 성공 조건과 변경 이력 | 사용자·회사 명시, 기존 문서에서 추출하면 추출 표시 |
| 계획·테스트 설계 | 계획 ID/버전, 요구사항 참조, 검사 목적·선정 이유, 적용 범위, 실행 명령, 예상 결과, 테스트 파일 버전, 제외 조건·변경 이유 | 에이전트의 명시적 요약과 문서; 내부 사고 과정 수집 불필요 |
| 검사 시도 | attempt ID, 계획·기준 버전, 실제 명령, 시작/종료, 종료코드·결과 요약, 환경·runner 버전, 검사 및 산출물 식별자/해시 | 로컬 runner의 실행 영수증 |
| 산출물 | 종류·버전·해시, 생성/변경 출처, 연결 목표·작업, commit 및 dirty 파일 manifest | 로컬 파일 관측과 명시적 연결 |
| 막힘·해결 | 실패 근거, 원인 가설/확인 구분, 시도한 해결, 도움 담당자·다음 조치, 해결한 재검증 참조 | 에이전트·담당자 기록과 실제 검사 근거 |
| Kit 운영 개선 | 적용한 Kit/철칙/하네스/스킬 버전, 루프 시도, 위반/누락 근거, 개선 가설, 변경, 재실행 결과, 적용/보류 | 설정 관측·gate 판정·담당자 판단 |

훅은 호출·변경·실행 경계를 관측합니다. 목표와 테스트 선정 이유는 기존 계획 문서에서 가져오거나 명시적으로 기록합니다. Handoff 계획/결과가 존재해도 실제 생성·검증·중앙 연결 여부를 각각 확인해야 합니다. PC 자동 전달을 기다리지 않고 파일 가져오기로 이 계약을 검증할 수 있습니다.

## 완료 판정과 신뢰 경계

계획된 검사와 실제 실행 명령, 기준 버전, 검사 대상 산출물 버전이 일치해야 현재 조건 충족으로 표시합니다. 관련 산출물 또는 기준이 바뀌면 이전 통과 이력은 남기고 재검증 필요로 표시합니다. 검사 기준 누락·실행 미관측·명령 불일치는 통과로 취급하지 않습니다. 해시는 동일성 확인이며 실행 사실이나 작성자의 신뢰를 보증하지 않습니다.

근거에는 작성 출처(선언/훅 관측/runner 관측/검토 확인), 검사 범위(작업/단계/프로젝트/업무 결과), 실행 환경(mock/local/browser/live provider/production), 최신성(current/stale/unknown)을 별도로 둡니다. 테스트 개수·세션 수·토큰 수로 개인 생산성이나 목표 진행률을 계산하지 않습니다.

## 대시보드와 실제 관리 조치

| 관리 질문 | 화면 근거 | 가능한 조치 |
|---|---|---|
| 회사 목표에 무엇이 기여하는가? | 목표·위임·프로젝트 연결과 확인된 업무 결과 | 누락된 기여 조건 명확화, 중복 작업 조정 |
| 왜 이 테스트를 하고 무엇이 빠졌는가? | 요구사항별 검사 계획·제외 이유·버전 변화 | 기준 보완, 범위 변경 검토 |
| 완성됐는가? | 현재 산출물에 대한 조건별 결과와 미검증 환경 | 승인, 재검증 요청, 실제 환경 검증 배정 |
| 어디서 막혔고 누가 도울 수 있는가? | 실패→수정→재시도, 원인 근거, 도움 담당자 | 전문 지원·접근 권한·의존 작업 조정 |
| Kit를 어떻게 개선할 것인가? | 반복 실패·규칙 누락·스킬/MCP 사용 근거와 개선 후 재실행 | 공통 설정 개선을 시험하고 효과 확인 후 배포 |

첫 화면은 목표별 현황과 지원이 필요한 항목, 상세는 계획·문서·검사 시도·산출물의 연결을 보여줍니다. MCP/데이터 접근은 실제 관측 또는 선언의 범위를 표시합니다. 호출이 있었다는 사실만으로 데이터가 결과물에 반영됐다고 판단하지 않습니다.

## Graphify 선택적 자동화

Graphify는 선행 필수 작업이 아닙니다. 코드 구조·영향 범위·관련 테스트 후보를 보강할 때 프로젝트별 opt-in으로 사용합니다. 기존 post-commit hook을 우선 활용할 수 있지만 미커밋 파일도 작업 대상이므로 commit만으로 최신성을 보증하지 않습니다. 매 도구 호출마다 전체 그래프를 재생성하거나 그래프 생성 실패로 구현·검증을 막지 않습니다.

기록할 것은 graph artifact ID, 생성기/버전, code-only 모드, 대상 프로젝트 범위, 소스 revision과 dirty manifest 해시, 생성 시각, 성공/실패/미관측, 최신성, 관련 작업/검사 참조입니다. AST 관계는 실행 경로·테스트 커버리지·목표 달성의 증거와 구분합니다. 홈 전체 인덱싱이나 전역 훅 설치는 하지 않습니다. 현재 연구 폴더의 Git 루트가 홈이므로 무조건 `graphify hook install`을 실행하면 프로젝트 범위를 벗어납니다.

## 다음 구현의 인수 조건

회사 결과 위임, 회사 작업 지시, 독립 개인 프로젝트를 두 사용자 이상에 연결합니다. 실제 로컬 검사에서 실패→수정→통과→산출물 변경→재검증 필요와 기준 개정 이력을 확인합니다. 명령·기준·산출물이 다른 영수증은 거부합니다. 관리자는 원래 목표, 테스트 선정 이유, 막힘, 지원 조치, 충족한 조건과 미검증 조건, Kit 개선의 근거를 화면에서 찾아야 합니다. 이 조건은 기존 합성 대시보드 릴리스 검사만으로 충족되지 않습니다.
