# 분석가: 이벤트 증거·데이터 아키텍처

작성·공식 문서 확인: 2026-09-30. 독립 초안. 다른 분석가 파일은 읽지 않았습니다. 구현·설정 변경·훅 설치를 수행하지 않았습니다. 이 문서의 모델·임계값·PoC는 AI 패널의 설계 제안이며 검증된 제품 성과가 아닙니다.

## 결론

**훅은 실행을 관찰하는 센서로 유효하지만, 프로젝트 의도와 승인과 완료를 스스로 증명하는 원장은 아닙니다.** 신뢰 가능한 첫 구조는 `승인된 작업 기준 버전 → 관찰된 실행 → 해당 버전의 결과물과 검증 증거`를 연결하고, 연결되지 않는 것은 명시적으로 미확인으로 남기는 구조입니다. 모든 작업을 완전하게 수집한다는 약속은 현재 확인한 공식 문서와 맞지 않습니다.

가장 작은 설계는 한 도구·한 로컬 Git 프로젝트부터 시작하는 관찰 기록과 검토 카드입니다. 카드에는 무엇을 하기로 했는지, 어떤 결과물이 생겼는지, 무엇이 실제로 검증됐는지만 표시합니다. WBS·간트 자동 복원, 범용 워크플로 엔진, 전 도구 통합, 업무 완료 자동 판정은 첫 구현의 필요조건이 아닙니다. 일정 계획에 필요한 의존성·기간·가용 인력은 훅에 없으므로 실행 시간으로 대체하면 안 됩니다.

## 최소 공통 모델

공통 템플릿은 모든 이벤트 payload를 하나로 평탄화하는 양식보다 **작은 공통 봉투와 명시적 연결**이어야 합니다. 초기에는 SQLite 한 파일과 별도 결과물 참조로 충분하다는 설계 가설입니다. 메시지 브로커·분산 그래프 DB는 필요성을 입증한 뒤 검토합니다.

### 1. 세 가지 기록을 섞지 않기

- **원시 관찰(raw event):** 공급자가 전달한 이벤트의 출처·ID·필드 존재 여부·수집 시각. 원본 payload는 기본 중앙 전송 대상이 아닙니다. 로컬 원본도 동의·보존 기간·민감 필드 정책이 필요하며, 삭제 또는 마스킹된 입력이라는 상태를 남깁니다.
- **해석(interpreted fact):** ‘작업 A와 관련 있을 가능성’, ‘범위 변경 후보’, ‘테스트 통과 보고’ 등. 원시 이벤트 참조, 추출 규칙/모델 버전, 근거 구절 또는 구조화 필드, 확신 상태를 붙입니다. 모델 재해석은 이전 해석을 덮어쓰지 않고 대체 관계를 남깁니다.
- **승인된 결정(approved decision):** 승인 주체·권한·시각·정확한 결정 버전·수락 기준. 에이전트 계획 업데이트나 추론은 자동으로 여기에 승격하지 않습니다. 사전 승인된 정책이 있다면 그 정책의 버전을 승인 근거로 참조합니다.

승인은 반드시 매번 새 UI 클릭을 뜻하지 않습니다. 기존 작업 지시·PR 검토 등에서 권한과 대상 버전이 명확한 행위를 재사용할 수 있습니다. 자유로운 대화의 ‘좋아요’를 무조건 승인으로 해석하지 않습니다.

### 2. 식별의 최소 단위

| 단위 | 최소 식별 | 혼동 방지 |
|---|---|---|
| 프로젝트 | 내부 project_id와 사용자가 확인한 저장소/자료 범위 매핑 | 원격 URL·폴더명은 변경·복제 가능하며 비밀도 포함 가능 |
| 저장소 / worktree | repo_id, worktree_id, 관찰한 HEAD, 로컬 경로 별칭 | 같은 저장소와 브랜치라도 별도 작업 공간일 수 있음 |
| 세션 / 실행 구간 | provider+native_session_id, 수집기 instance/epoch, run_id | resume과 새 작업, 프로세스 재시작을 구분 |
| 에이전트 / 호출 | native agent_id·parent_id·tool_call_id가 있으면 보존; 없으면 unknown | 모델명은 에이전트 정체성이 아님; 추측 부모 금지 |
| 이벤트 | 최초 로컬 기록 때 고정한 event_id, source ID(있으면), schema/adapter 버전 | 전송 재시도 때 새 ID를 생성하지 않음 |
| 결과물 | artifact_id + version_id + locator + 관찰 시각 | 파일 경로만 저장하면 이후 편집으로 과거 증거가 바뀜 |
| 작업/결정 | work_item_id + decision_revision + acceptance criteria | 계획 변경 전후와 실행 결과를 구별 |

커밋된 코드의 결과물 참조는 commit과 파일 경로를 사용합니다. 미커밋 결과물은 승인된 파일 집합의 내용 digest와 부모 상태를 참조하고, 필요하면 로컬 스냅샷을 사용합니다. 작업 중인 전체 디스크 해시나 모든 파일 복제는 하지 않습니다. 동일 worktree를 여러 에이전트가 동시에 수정했다면 해시만으로 작성자를 구분할 수 없으므로 공동/미확인 귀속으로 표시합니다. 외부 문서라면 공급자 revision이 있을 때 사용하고, 없으면 ‘현재 링크’와 ‘검증 당시 버전’을 구별합니다.

### 3. 인과관계와 누락

공통 이벤트 봉투에는 occurred_at(있으면), observed_at, received_at, collector_epoch와 local_sequence, causation_ref(명시적일 때), native IDs, coverage 상태를 둡니다. local_sequence는 수집 순서이며 실제 실행 순서라는 보장은 없습니다. 기기 시계 또는 업로드 순서로 전역 인과관계를 만들어서는 안 됩니다. 도구 호출 ID와 부모-자식 ID, 특정 결과물 버전을 사용한 기록만 인과 연결의 근거로 승격합니다. 그 외는 시간상 인접 또는 추정 연결입니다.

초기 전달 모델은 **로컬 영속 기록 이후 적어도 한 번 전송 + 서버 event_id 중복 제거**로 충분합니다. 중앙 연결은 이 문서의 제안이며 이번에 생성하지 않습니다. 안정적 공급자 event ID가 없으면 공급자가 새로 발생시킨 동일 payload 이벤트까지 완벽히 중복 제거할 수 없습니다. 내용이 같은 두 호출을 하나로 합치지 말고 ‘동일 가능성’으로 남겨야 합니다.

훅 실행 전에 프로세스가 죽거나 로컬 기록 전에 실패한 이벤트는 복구할 수 없습니다. sequence가 연속이라는 이유로 원천 누락이 없다고 판단하지 않습니다. 시작 시 수집 가능 범위를 기록하고, 저장 실패·대기열 용량 초과·미확인 종료를 표시합니다. SessionEnd에 최종 flush를 의존하지 않고 다음 실행에서 미전송 기록을 이어 보냅니다. 끝 이벤트가 없는 작업은 타임아웃 후 성공/실패가 아닌 ‘종료 미확인’입니다. 첫 PoC에서 heartbeat 서비스까지 추가할 필요는 없고 마지막 관찰 시각을 보여주면 됩니다.

## 계획 범위·실제 범위·완료의 연결

작업 기준은 ‘목표 한 문장, 포함/제외 범위, 수락 기준, 승인된 revision’으로 제한합니다. 실행이 시작될 때 그 revision에 연결하며 중간 변경은 새 revision과 이유를 남깁니다. 기존 계획을 사후 실제 결과로 덮어쓰면 범위 변경 자체가 사라집니다.

실제 범위는 관찰된 파일·외부 자원·검증 활동입니다. 파일 수·토큰 수·수행 시간으로 기능 완성률을 계산하지 않습니다. 파일 변경 집합과 제품 기능 범위는 다른 개념이므로 AI가 제안한 범위 차이는 검토 후보로 남깁니다.

완료 상태는 최소한 `실행 관찰`, `결과물 있음`, `검증 증거 있음`, `수락됨`을 구별합니다. 검증 증거에는 대상 결과물 버전, 환경(local/staging/production 등), 명령/검증 방법, 결과와 시각을 붙입니다. 테스트 통과 후 코드가 다시 바뀌면 이전 결과가 새 버전의 증거로 자동 이전되지 않습니다. 최종 수락은 기준별 증거와 권한자의 판단을 결합합니다. 모든 작업에 형식적 수락 버튼을 강제하지 않고 기존 검토 절차를 재사용합니다.

회의·메신저·디자인 툴 등 훅 밖 결정은 영구적인 공백입니다. 최초 설계는 사용자가 기존 자료 링크와 결정 한 문장을 연결하고 필요 시 승인하는 방식이면 충분합니다. 링크만 있고 읽기 권한이나 버전이 없으면 ‘참조 있음, 내용 미검증’입니다. 커넥터를 전부 연결해 공백을 메우려 하면 보안·유지비·권한 문제가 먼저 커집니다.

## Frame과 Tool의 유연성

Frame은 작업을 보는 구조(단계·역할·수락 기준·의존 관계), Tool은 관찰과 결과물을 제공하는 도구입니다. 둘을 분리합니다. 첫 모델의 공통 축은 `작업/결정/실행/결과물/검증/수락` 여섯 개면 충분합니다. 소프트웨어에는 커밋·테스트, 디자인에는 문서 revision·검토, 조사에는 출처·보고서가 결과물 유형으로 들어갑니다.

프로젝트별로 단계 이름과 결과물 유형 몇 개를 설정하고, 사용자가 선택한 프레임의 버전을 남깁니다. AI가 단계 전환을 제안할 수 있지만 도구가 바뀌었다고 프로젝트 단계를 바꾸지는 않습니다. 새로운 템플릿 언어·플러그인 마켓·범용 DSL은 첫 검증 범위에서 제외합니다. 두 번째 실제 작업 유형을 설명할 때 공통 축이 깨지는지 먼저 확인합니다.

## 유지비·수집 보안·관찰자 효과

- 도구별 어댑터는 event names, 필드, 버전, frontend/hosted 경로에 대한 capability manifest를 가져야 합니다. ‘지원함’ 대신 ‘이 버전·경로에서 이런 이벤트를 확인함’을 표시합니다. 업데이트 때 소수 대표 fixture와 실제 시나리오를 재검증해야 하므로 네 도구 동시 지원은 단순 네 배가 아니라 조합 유지비를 만듭니다.
- 기본 전송은 도구 종류, 상태, 익명화된 프로젝트/결과물 참조, 필요한 ID로 제한합니다. 전체 prompt, shell 인자, stdout, 환경변수, 원격 URL을 자동 전송하지 않습니다. 경로와 파일명 자체도 민감할 수 있습니다. 정규식 비밀 탐지만으로 안전을 보장하지 말고 수집 허용 목록을 우선합니다.
- 원문을 제한하면 범위 변경 이유를 자동 해석할 수 있는 능력도 줄어듭니다. 이 충돌은 설계상 사실입니다. 로컬 해석과 사용자가 선택한 짧은 요약을 후보로 쓰고, 정확성이 부족하면 자동 복원을 포기해야 합니다.
- 로깅 입력은 비신뢰 데이터입니다. 명령으로 실행하지 않고 크기·형식 제한을 둡니다. LLM 요약에도 데이터 속 지시를 승인 명령으로 승격하지 않습니다. 중앙화 시 프로젝트별 접근 제어·삭제·보존 기간·내보내기가 추가 필수 비용입니다.
- 관찰 훅은 네트워크 응답과 LLM을 기다리지 않고 짧은 로컬 기록 후 반환해야 합니다. 기존 훅의 차단·승인 의미를 바꾸지 않습니다. 단, 비차단 운영에서는 기록이 누락될 수 있으므로 완전한 감사와 작업 무중단을 동시에 보장하지 않습니다.
- 관찰이 에이전트 컨텍스트를 계속 주입하거나 작업 문서를 자동 수정하면 행동 자체가 달라집니다. 첫 실험은 읽기 중심으로 두고, 도구 실행 시간·토큰·수정 행동의 변화를 비교합니다.

지원 밖은 숨기지 않습니다. 훅 미설치/미신뢰, 미검증 버전, hosted 경로, 수동 편집, 다른 기기, Git 밖 자료, 공유 worktree의 동시 수정, 끊긴 외부 링크를 coverage에 표시합니다. 이 경우 화면은 ‘미관찰’을 나타내야 하며 0 또는 완료로 채우지 않습니다.

## 핵심 가정

1. 사용자가 작업 시작 또는 범위 변경 시 기존 지시를 결정 기준에 연결하는 작은 행동은 받아들일 것입니다(Unverified).
2. 최소 메타데이터와 선택적 짧은 근거만으로 유용한 연결을 만들 수 있을 것입니다(Unverified). 원문 전체가 필요하면 수집 모델을 재설계해야 합니다.
3. 초기 작업에서 로컬 Git 결과물과 소수 검증 명령이 핵심 결과의 상당 부분을 나타낼 것입니다(Unverified). 디자인·운영 업무 전반으로 일반화하지 않습니다.
4. 호스트가 제공한 이벤트 내용은 운영 가시성 용도로 신뢰하되 악의적 로컬 변조에 대한 감사 증거를 요구하지 않을 것입니다(Unverified).

## 추가 확인이 필요한 증거와 수집 방법

구현 승인 전에는 먼저 공개 fixture와 수작업 표로 데이터 모델을 검증할 수 있습니다. 이후 별도 승인된 임시 테스트 리포에서 한 도구의 관찰 PoC를 수행합니다. 공식 문서만으로 실제 coverage와 지연을 확정하지 않습니다.

| PoC 시나리오 | 대조할 독립 정답 | 통과 조건 제안 |
|---|---|---|
| 일반 작업과 테스트 후 재수정 | 수동 시나리오 기록·결과물 버전 | 이전 테스트를 새 버전의 완료 근거로 표시하는 오판 0건 |
| 병렬 agent + 두 worktree | 명시적으로 배정한 작업·실제 변경 버전 | 잘못된 단독 작성자/작업 귀속 0건; 모호하면 unknown |
| 프로세스 강제 종료·재시작·resume | 프로세스 조작 기록·로컬 spool | 종료 누락을 성공으로 처리 0건; 영속화된 이벤트 전량 복구 |
| offline·재전송·순서 뒤바뀜 | 고정 event ID를 가진 fixture | 중앙 중복 노출 0건; 인과 연결 유지, 시각순 인과 발명 0건 |
| 동일 명령 연속 2회 | 별도 호출 ID 또는 수동 정답 | 서로 다른 호출을 payload 중복으로 합치지 않음 |
| 미지원 hosted 경로·훅 비활성 | 직접 실행한 동작 목록 | 해당 경로를 관찰 완료로 오표시하지 않음 |
| 민감 문자열 심기 | 합성 토큰·개인정보·파일 경로 | 허용하지 않은 원문 외부 전송 0건 |
| 범위 변경·회의 결정 | 사람이 확정한 기준 revision | 추정 결정을 승인으로 승격 0건; 이전/현재 기준 분리 |

수치 기준은 검증된 업계 기준이 아닙니다. 초기 제안은 훅 자체 p95 추가 지연 100ms 이하, 업무당 연결 확인 1분 이하, 사전 정의된 관찰 대상 활동의 수집률 95% 이상입니다. 전체 작업 수집률이라고 표현하지 않습니다. 20~30개 의도적 실패 시나리오에서 우선 오판을 제거한 뒤 실제 업무의 모호한 사례에서 정밀도·미연결률을 측정합니다. 소수 테스트에서 0건이라고 장기 신뢰성을 확정하지 않습니다.

## 결론을 반증할 조건

- 승인된 결정 기준 없이도 여러 실제 프로젝트에서 외부 결정·범위 변경·완료를 독립 정답과 일치하게 복원한다면 수동 기준 연결을 줄일 수 있습니다. 지금은 그 증거가 없습니다.
- metadata-only에서 연결 불가능한 핵심 결정이 반복되고 원문 수집도 허용되지 않는다면 훅 중심 설계를 중단하고 명시적 결정 기록 중심으로 전환합니다.
- 실용 버전에서 호출 ID·agent 관계가 부족해 병렬 활동 귀속 오판을 제거할 수 없다면 해당 환경은 통합 대상에서 빼거나 세션 단위 가시성으로 낮춥니다.
- 실패 시나리오에서 증거 없는 완료를 계속 생성하면 완료 자동 요약 기능을 제외하고 원시 관찰·결과물 링크만 제공합니다.
- 유지해야 하는 어댑터 조합이나 관찰 지연이 허용 수준을 넘으면 지원 도구 하나로 좁히고 Git/CI 결과물 증거 중심으로 전환합니다.
- 사용자에게 필요한 결과가 악의적 변조까지 방어하는 법적 감사라면 이 최소 구조는 부족합니다. 서명·신뢰된 외부 시각·독립 시스템 증거가 별도 과제이며 현재 제안을 확장한다고 간단히 해결되지 않습니다.

## 확신도와 이유

**Certain:** 확인한 문서상 이벤트 범위·종료 보장·필드·Git worktree 의미·OTel/PROV 개념. 단, 실제 설치환경의 구현 동작은 미검증입니다.

**Likely:** 원시 관찰/해석/승인을 분리하고 결정·결과물 버전을 연결하는 모델이 로그의 과잉 주장을 줄입니다. 명시적 인과 ID, 로컬 영속화, 재시도 중복 제거, unknown 상태는 문서상 누락·비동기 특성에 직접 대응합니다.

**Unverified:** 이 최소 구조의 실제 수집률, 사용자의 확인 부담, 네 도구 호환성, 원문 최소화 상태에서의 해석 정확도, 비용 대비 실무 효용. 이번 분석은 이를 검증했다고 주장하지 않습니다.
