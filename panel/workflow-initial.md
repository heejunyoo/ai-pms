# 분석가: 업무·인간-AI 협업 근거

작성·출처 확인: 2026-09-30. 독립 초기 의견. 다른 분석가 파일을 읽지 않았으며, 실제 인터뷰를 수행하지 않았다.

## 결론

**조건부로 검증할 가치가 있다. 첫 대상은 비개발자 전체보다, 제품 책임자와 기술 검토자가 나뉜 2~5명 팀이며, 첫 사용 사례는 ‘AI가 만든 변경을 다음 사람에게 넘기기 전, 합의한 범위와 검증 상태를 확인하는 일’이다.** 팀 규모와 수치는 시장 근거가 아닌 모집 가설이다. 대시보드가 누구의 결정을 바꾸는지 특정해야 한다. 제품 책임자는 ‘이 변경을 이번 출시 범위에 넣을 것인가’, 기술 검토자는 ‘추가 확인 없이 인수할 수 있는가’를 결정한다. 통합 전 이 두 결정의 시간과 오류를 줄이면 사용 가치가 생긴다. Agent 활동량이나 자동 복원한 Gantt만 늘리면 가치가 입증되지 않는다.

가시성이 낮아졌다는 주장은 미검증이다. 더 정확한 원인 후보는 (1) 합의 전 생산량 증가, (2) 대화·코드·검증 결과 사이의 연결 부재, (3) 산출물에 대한 신뢰와 실제 확인의 간극, (4) 병렬 작업으로 인한 주의 분산이다. 다만 AI 이전부터 있던 불명확한 책임, 고객 이해 부족, 지나치게 큰 작업 단위, 부실한 테스트가 원인일 수 있다. 이 경우 관찰 도구만으로는 해결되지 않는다.

## 핵심 근거

1. **METR 무작위 실험, 2025-07-10.** 숙련된 오픈소스 개발자 16명이 익숙한 성숙 프로젝트에서 246개 작업을 수행했을 때 당시 AI 허용 조건은 작업 시간이 19% 길었다. 개발자의 체감과 측정 결과가 달랐다는 점은 ‘빨라 보인다’를 가치 지표로 쓰면 안 된다는 근거다. 비개발자, 신생 앱, 2026년 도구에 일반화할 수 없으며 문서 가시성 저하를 측정한 실험도 아니다. [원문](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)

2. **METR 후속 설계 변경, 2026-02-24.** 연구진은 후속 자료에 AI 없이 일하기 싫어하는 개발자·작업의 선택 편향, 낮아진 보수, 병렬 Agent의 시간 측정 문제가 있다고 밝혔다. 현재 효과의 신뢰할 만한 추정치로 취급하지 않는다. 따라서 19% 수치를 현재의 AI 비효율 증거로 고정하면 안 된다. 공개된 익명 개발자 원문: “I really like using AI!” 이 견해는 채택 유인을 보여주지만 생산성이나 관리 도구 구매의사를 입증하지 않는다. [원문](https://metr.org/blog/2026-02-24-uplift-update/)

3. **Lee 외, CHI 2025, 2025-04.** 지식근로자 319명의 936개 사용 사례 설문에서 AI 신뢰가 높을수록 비판적 사고 노력을 덜 보고하는 관계가 있었고, 사고의 초점은 검증·결과 통합·업무 감독으로 이동했다. 사람에게 ‘판단에 필요한 근거’를 제공할 이유는 있다. 자기보고·상관관계 연구이므로 인지능력 퇴화나 개발팀의 성과 악화를 증명하지 않는다. [연구 원문 소개](https://www.microsoft.com/en-us/research/publication/the-impact-of-generative-ai-on-critical-thinking-self-reported-reductions-in-cognitive-effort-and-confidence-effects-from-a-survey-of-knowledge-workers/)

4. **DORA, User-centric focus, 2026-01-12 갱신(2025 연구 해설).** 사용자 필요에 맞춘 우선순위가 AI의 효과를 좌우하며, AI가 기존 조직의 강점과 약점을 증폭한다는 연구 해석을 제시한다. 산출량과 고객 가치를 구별해야 한다는 근거다. 이 자료는 조직 수준 연관·연구진의 해설이며 ‘PMS를 설치하면 좋아진다’는 개입 실험이 아니다. [공식 자료](https://dora.dev/capabilities/user-centric-focus/)

5. **Addy Osmani의 공개 실무 기록, 2025-12-18.** 원문 “Start with a clear plan (specs before code)”는 본인이 요구사항·계획을 먼저 구체화하고 작은 단위로 실행한다는 설명이다. 병렬 Agent 감시가 정신적으로 부담되어 주 Agent 하나와 보조 검토를 주로 쓴다고도 기록한다. 문서가 사라지는 것이 필연이라는 주장에 대한 반례다. 숙련자의 자기선택 사례이며 이 방식이 모든 팀에 최적이거나 유료 PMS 수요가 있다는 증거는 아니다. [본인 원문](https://addyo.substack.com/p/my-llm-coding-workflow-going-into)

6. **Simon Willison의 본인 인터뷰 정리, 2026-05-06.** 원문 “Claude Code does not have a professional reputation!”은 Agent에 인간 팀 같은 책임성을 부여할 수 없다는 문제 제기다. 본인도 Agent 신뢰가 높아지며 모든 줄을 검토하지 않게 되었고, 실제 사용 경험을 산출물의 외형보다 중시한다고 설명한다. 관리 대상이 코드 작성 과정에서 수용 근거와 책임으로 옮겨갈 수 있음을 시사한다. 개인의 경험과 견해이며 기능의 안전성이나 보편적 행동의 근거는 아니다. [본인 원문](https://simonwillison.net/2026/May/6/vibe-coding-and-agentic-engineering/)

## 문서 없는 관찰과 최소 개입 UX

관찰로 확인할 수 있는 것은 ‘어떤 입력 뒤 어떤 도구가 실행되었고 어떤 결과가 남았는가’다. 사용자 발화에 명시된 요청은 **진술된 의도**의 증거이지만 팀이 합의한 범위와 같지 않다. 마지막 프롬프트가 공식 결정인지 탐색인지, 테스트 통과가 고객 수용인지, 실행 계정의 소유자가 결과 책임자인지는 이벤트만으로 확정할 수 없다. 오프라인 대화와 누락된 도구 경로가 있으면 더욱 그렇다. Phase는 목표·진입/종료 기준이 합의된 경우에만 확정하고, 없으면 ‘추정 단계/확인 필요’로 표시해야 한다.

사후 로그는 실제 변경과 설명을 연결해 복구 비용을 줄인다. 사전 기획은 무엇을 만들지·만들지 않을지와 수용 조건을 정하여 불필요한 생성을 막는다. 전자는 후자를 대체하지 못한다. 이미 진행한 이유를 AI가 사후에 그럴듯하게 쓰는 것은 결정 증거가 아니다.

최소 개입은 기존 PR·공유 직전 화면에 붙는 카드 하나다. ‘이번 목표 1줄 / 이전 합의와 달라진 점 / 관찰된 검증과 미확인 항목 / 결정할 사람’을 근거 링크와 함께 제안한다. 사용자는 **범위 유지·변경 승인·판단 보류** 중 고르고 잘못된 문구만 고친다. 최초 작업에서 목표·수용 조건·책임자만 확인하고 이후에는 의미 있는 범위 변화나 인수 때만 질문한다. 모든 tool call 승인이나 매일 일지 작성을 요구하지 않는다. 책임자를 추측해서 배정하지 않으며, ‘담당자 미확인’을 허용한다. 코드·원문을 중앙으로 보내는 실험 없이도 참여자가 허용한 발췌와 로컬 자료로 이 UX의 가치를 먼저 검증할 수 있다.

## 핵심 가정

- Unverified: 작은 팀에서도 합의와 실제 변경의 차이가 반복적으로 재작업을 만든다.
- Unverified: 기존 작업 화면의 짧은 확인이라면 작성 부담보다 의사결정 이득이 크다.
- Unverified: 기술 검토자가 카드의 근거를 읽고 추가 확인을 요청할 권한과 시간을 가진다.
- Likely: 변경 이력은 사후 설명을 도울 수 있지만 합의·책임에는 사람의 명시 확인이 필요하다.

## 결론을 반증할 조건

실제 사례에서 손실 원인이 범위 오해가 아니라 테스트·기술 역량 부족이고, 카드를 봐도 수용 판단이 달라지지 않으면 PMS 가설을 접는다. 기존 PR 템플릿과 5분 체크인으로 같은 효과가 나면 중앙 제품을 만들 이유가 약하다. 많은 확인을 요구해야만 정확해지거나, 오류 정정 시간이 절감 시간보다 길면 자동 복원 접근을 축소한다. 유용하다고 말하지만 반복 사용·유료 연장을 거절하면 구매 문제로 취급한다.

## 확신도와 이유

Certain: 위 공개 자료에서 기술한 연구 조건·한계와 실무자의 발언을 확인했다. Likely: 관찰 자체보다 범위 수용과 검증 요청의 결정 지원이 더 좁고 검증 가능하다. Unverified: 2~5명 팀의 실제 수요, 도입 빈도, 지불의사. 공개 근거 어느 것도 이 제품의 시장성을 입증하지 않는다.

## 추가 확인이 필요한 증거와 수집 방법

1. 제품을 설명하기 전에 후보 8개 팀에서 최근 2주간 실제 인수 실패 1건과 잘된 사례 1건씩 재구성한다. 누가 언제 무엇을 결정했고 어떤 자료를 찾느라 시간을 썼는지, 기존 도구가 왜 부족했는지 확인한다. AI 사용 이전부터 같은 문제가 있었는지도 묻는다. 실패 사례만 모으면 가설을 강화하는 편향이 생긴다.
2. 자발적 동의를 받은 4~6개 팀의 2주 실험을 제안한다. 신규 훅 설치 없이 허용한 기존 자료로 사람이 카드 초안을 만드는 concierge 방식이다. 첫 주 현재 방식, 다음 주 카드 사용을 비교하되 학습·순서 효과가 있으므로 인과 증명으로 부르지 않는다. 가능하면 유사 작업끼리 순서를 바꾼다.
3. 활동량 대신 ‘담당자가 목표·범위 변경·미확인 항목을 정확히 답하는 데 걸린 시간’, 실제 추가 검증/범위 축소 결정, 오판과 재작업, 카드 정정 시간, 다음 인수 때 자발적 재사용을 기록한다. 정답은 실행자와 수용자의 별도 확인 및 실제 결과로 대조한다. 분모에는 제안했으나 무시한 카드도 포함한다.
4. 사전에 정할 탐색 기준 예: 6개 팀 중 4개가 도움 요청 없이 두 번 이상 재사용, 중앙값 판단 준비시간 30% 감소, 중요한 오확신 증가 없음, 2개 이상이 가격이 명시된 유료 연장에 동의. 이 숫자는 연구 결과가 아닌 제품팀의 중단 기준 제안이다. 미달 시 기존 PR 템플릿 지원으로 축소하거나 검수·요구사항 정리 서비스로 문제를 다시 정의한다.
