# 분석가: 도입·대체재·구매 행동

작성·출처 확인일: 2026-09-30. 독립 초기 분석. 다른 패널 파일은 읽지 않았다. 실제 고객 인터뷰·제품 설치·유료 실험은 수행하지 않았다. 아래 Certain은 **공식 문서에 해당 기능이 명시됨**을 뜻하며 실제 현장 성과를 뜻하지 않는다.

## 결론

**범용 AI PMS와 훅 수집 대시보드에 바로 진입하지 않는 것이 타당하다(Likely).** 세션을 코드에 연결하는 영역은 Entire, 공유 명세로 에이전트를 지휘하는 영역은 Intent/Kiro, 사람의 책임과 이슈를 유지하는 영역은 Linear, PR·세션 통합은 GitHub, 여러 에이전트를 칸반으로 실행·검토하는 영역은 Vibe Kanban이 이미 직접 다룬다. “여러 AI의 작업을 한눈에”는 차별화 주장으로 약하다.

검증할 가장 좁은 후보는 **비개발자 발주자/PM과 AI를 쓰는 구현 담당자가 매주 기능을 인수할 때, 합의한 범위와 실제 결과 사이의 차이를 근거와 함께 확인하는 인수 검토 카드**다. 대상은 2~8명 정도의 소규모 제품팀 또는 소프트웨어 제작 대행팀이라는 실험 가설이다. 제품명은 중요하지 않다. 사용자가 실제로 내려야 하는 결정은 “이번 변경을 승인할 것인가, 무엇이 합의 밖인가, 누가 답해야 하는가”다.

한 장에 ① 마지막으로 사람이 승인한 범위 버전 ② 추가·삭제·미완료 후보 ③ 이슈/PR/데모/선별 세션 근거 ④ 아직 확인할 수 없는 내용 ⑤ 답할 사람과 다음 승인 질문을 둔다. 기존 Linear/GitHub/문서가 업무의 원본이고 새 도구는 **검토 자료를 준비하는 보조물**이어야 한다. 범위 변경을 자동 확정하거나, 활동량으로 진척률을 만들거나, 새 WBS 작성부터 요구하면 첫 효용보다 비용이 앞선다.

이 제안 역시 수요가 확인된 제품은 아니다(Unverified). 첫 실험은 훅 설치 없이 기존 자료로 유료 검토 카드를 수작업 제공하는 것으로 충분하다. 이 카드가 구매로 이어진 뒤에만 자동 수집의 추가 가치를 따로 검증한다.

### 2. 어디서 차별화가 남는가

**기술 데이터가 아니라 의사결정의 공백이 후보이다.** 기록이 있다는 사실은 “이 변경을 누가 승인했는가”, “이번 인수 범위인가”, “데모는 통과했지만 운영 확인은 남았는가”에 자동으로 답하지 못한다. 특히 최종 결정이 전화·회의·메신저에 있으면 코딩 trace가 풍부해도 합의는 비어 있다. 이 빈틈은 새 제품의 기회인 동시에 치명적인 입력 문제다. 기록되지 않은 승인 이유를 생성하면 제품은 신뢰를 잃는다.

쉽게 복제되는 부분은 세션 요약, 자동 칸반, agent별 실행 수, 타임라인, 문서 템플릿, WBS 생성이다. 기존 제품이 데이터와 배포 채널을 이미 갖는다. 상대적으로 방어 가능성이 있는 부분은 **구체적 인수 업무에서 반복 검증된 판단 양식, 잘못된 주장에 대한 정정 이력, 기존 책임자에게 최소 질문으로 확인받는 사용 습관**이다. 다만 이것도 현재는 가설이며 데이터가 쌓인다는 이유만으로 moat가 생기지 않는다. 고객 간 비공개 결정 데이터를 임의로 재활용할 수도 없다.

멀티 agent 지원과 멀티 사용자 지원을 구분해야 한다. agent 여러 개의 실행 상태를 보여주는 일보다, 사람이 합의한 범위를 고정하고 서로 다른 사람이 같은 결과를 다른 의미로 해석할 때 승인 권한을 정리하는 일이 제품의 어려운 부분이다. 반대로 대상이 혼자 만드는 사람이라면 조직 책임 기능은 과하다. 이 경우 Entire나 Kiro의 재개·계획 기능으로 충분할 수 있다.

### 3. 사용자·구매자와 설치·공유의 교환 조건

| 상황 | 실제 사용자 / 구매자 | 돈이나 설치를 감수할 만한 작은 효용(가설) | 거절할 이유 |
|---|---|---|---|
| 개인 비개발자 제작자 | 본인 / 본인 | 며칠 뒤 돌아와 5분 안에 현재 상태와 다음 확인을 재개 | 무료 agent 요약·기존 채팅으로 충분, CLI·Git 개념 자체가 장벽 |
| PM+AI 구현자 소규모 팀 | PM 및 구현자 / 팀 리드·대표 | 주간 인수 준비와 범위 확인 시간을 줄이고 합의 누락으로 인한 재작업 방지 | PM만 이익을 보고 구현자가 설치·정정 비용을 부담, 기존 Linear 이중 입력 |
| 대행·외주 제작 | 제작 PM 및 검토 고객 / 대행사 대표 또는 발주 책임자 | 추가 요청인지 원래 범위인지 근거로 확인하고 승인 지연을 줄임 | 법적 효력/완전한 감사 추적을 기대하면 초기 제품 능력 초과, 고객 정보 공유 금지 |
| 큰 개발 조직 | EM·PM / 보안·구매·조직 책임자 | 반복되는 cross-team 인수의 증거 준비 | 승인과 rollout 비용이 높고 GitHub/Linear 계약에 기능이 흡수될 수 있음 |

첫 후보는 **이미 매주 인수가 있고, 적어도 두 사람이 범위에 합의하며, 구현 담당자 한 명이 기존 자료를 제출할 수 있는 작은 팀**이다. 비개발자 전체를 고객으로 묶지 않는다. 사용자가 직접 훅을 설치해야만 결과를 볼 수 있으면 초반 타깃과 맞지 않는다. PM는 링크 기반 검토 화면만 사용하고 구현자가 제한된 자료를 선택하는 형태를 우선 실험한다.

데이터공유 대가는 추상적 가시성이 아니라 당장 오늘 인수할 기능의 질문 감소여야 한다. 원문 전량 전달 없이도 필요한 근거를 만들 수 있어야 한다. 고객이 원문을 공개하지 않으면 “미확인”을 유지해야 한다. 원문을 더 내도록 압박하는 제품은 협업 신뢰를 훼손할 수 있다.

### 4. 사용량 지표가 감시로 바뀌는 위험

Entire는 2026-04-06 발표에서 사용자별 checkpoint 수, agent별 checkpoint 수와 commit 수의 집계를 설명한다([공식 발표](https://entire.io/blog/entire-dispatch-0x0008)). Linear도 Delegate별 Insights를 설명한다([문서](https://linear.app/docs/agents-in-linear)). 이는 **집계 기능 존재**의 근거이며 직원 감시로 실제 오용되었다는 증거는 아니다.

그러나 새 제품이 개인별 prompt·token·작업시간·agent 실행량을 보여주면 구매자는 이를 생산성 순위로 읽을 유인이 있다(Likely). 어려운 일, 검토·숙고, 비공개 상담, 다른 도구 작업은 기록량에 제대로 나타나지 않는다. 기록 누락도 저성과처럼 보일 수 있다. 설치자는 자신의 작업이 평가로 전용된다고 느끼면 기록을 줄이거나 의미 없는 활동을 늘릴 수 있다(미검증 행동 가설).

초기 산출물은 개인 순위 대신 **인수 대상별 근거 충족·미확인·승인 대기**를 보여줘야 한다. 어떤 자료가 수집·공유되는지 당사자가 볼 수 있고, 초안·사적 세션을 제외하고, 잘못 연결된 사실을 정정할 수 있어야 한다. 이 요구는 별도 보안 제품을 만들자는 뜻이 아니라 협업 도입의 최소 조건이다.

### 5. 공개 고객 근거가 말하는 것과 말하지 않는 것

- [Linear 고객 목록](https://linear.app/customers)은 Ramp의 coding agent PR 사례, Coinbase의 agent-first 사례와 여러 조직의 채택을 제시한다. 기존 업무 원본 위에 agent를 붙이는 실제 조직 사례가 있다는 vendor evidence다. 별도의 중립 AI PMS에 지불할 의사는 입증하지 않는다. 목록의 성과 수치를 비교 가능한 독립 평가로 사용하지 않았다.
- [Augment 고객 사례 목록](https://www.augmentcode.com/customers)은 Intercom의 병렬 agent workflow와 MongoDB의 기존 workflow 내 CLI 활용 발언을 싣는다. 이는 기존 업무 연결의 중요성을 시사하지만 Augment 전반의 사례를 Intent 자체의 성과로 바꾸면 안 된다. Intent의 좁은 기능이 얼마나 인수 시간을 줄였는지는 미확인.
- [Entire 공개 해커톤 사례](https://entire.io/blog/how-the-sentiment-maxxers-mogged-their-way-to-hackathon-glory-with-entire)는 commit과 개발 trace를 연결한 사용을 설명한다. 장기 유료 팀 수요나 비개발자 채택의 증거는 아니다. 과거 저장 형식도 현행과 다를 수 있다.

## 핵심 가정

1. 팀이 실제로 비용을 느끼는 문제가 '누가 어떤 agent를 썼는지'보다 '합의한 결과를 인수할 수 있는지'에 있다(Unverified).
2. 현재 이슈·PR·문서만으로 초안의 상당 부분을 만들 수 있고, 누락된 의사결정은 짧은 확인 질문으로 보완 가능하다(Unverified).
3. 과거 승인 범위는 최소한 하나의 문서나 메시지로 식별 가능하다. 없다면 로그 해석 제품보다 승인 습관 정립이 선행되어야 한다(Likely).
4. 기존 도구 원본을 유지하면서 제안된 카드에 반복 접근할 이유가 생긴다(Unverified).
5. 한 구현자의 자료 제공 비용보다 PM/검토자와 그 구현자가 함께 절약하는 비용이 크다(Unverified).

## 결론을 반증할 조건

- 기존 Linear/GitHub+팀 템플릿으로 같은 인수 결과를 같은 시간에 만들고 사용자가 차이를 구분하지 못하면 별도 제품 진입 주장을 철회한다.
- 고객이 원하는 것이 검토 자료가 아니라 agent 실행·복구이고 Entire/Intent/Vibe Kanban으로 해결하면 해당 도구의 활용 지원으로 전환한다.
- 실제 불편은 승인 지연이 아니라 요구 자체의 불안정성이고 누가 승인할지 정해지지 않았다면 자동 수집을 중단하고 책임·의사결정 운영 문제로 재정의한다.
- 훅 설치와 광범위한 원문 전송을 요구해야만 유용한 결과가 나오지만 대상 팀이 이를 거부한다면 타깃을 바꾸거나 중단한다.
- 현행 제품이 이미 같은 인수 검토를 더 낮은 비용으로 제공한다는 실제 시연이 나오면 '남는 공백' 평가를 수정한다.

## 확신도와 이유

- **Certain:** 여섯 공식 제품이 각각 trace, spec, issue, session, agent orchestration의 상당 부분을 문서상 제공한다. broad AI PMS는 빈 시장이 아니다.
- **Likely:** 기존 도구를 대체하는 것보다 기존 원본에 근거한 좁은 인수 업무가 전환 비용을 줄인다. 다만 실제 채택을 측정하지 않았다.
- **Unverified:** 제안한 첫 고객, 지불의사, 설치 수용도, 카드 정확도·시간 절감, 차별화 지속성. 제품 공식 문서와 vendor 사례만으로 확정할 수 없다.

## 추가 확인이 필요한 증거와 수집 방법

아래 수치와 가격은 시장 통계가 아니라 실험 전 정할 의사결정 기준의 제안이다. 이번 조사에서는 모집·접촉·결제·설치하지 않는다.

1. **문제 면담 8~12팀:** 최근 한 달의 실제 인수 한 건을 재현한다. 어디서 범위를 합의했는지, 마지막 변경이 왜 들어갔는지, 누구에게 몇 번 물었는지, 재작업 사례와 시간을 확인한다. '쓰실 건가요' 답변보다 실제 자료와 행동을 받는다. 과반이 구체 사건을 제시하지 못하면 범용 팀 PMS 가설을 보류한다.
2. **대체재 대결:** 4~6팀의 최근 실제 작업에서 기존 방식/기존 도구의 요약과 인수 카드를 비교한다. 같은 승인자에게 핵심 질문의 정답·근거 찾는 시간·잘못된 확신을 측정한다. 미관 선호와 실무 효용을 분리한다. 이미 잘 관리되는 팀도 포함해 선택 편향을 줄인다.
3. **2주 유료 concierge:** 6개 적합 팀에 프로젝트당 10만원의 시험 가격을 제시하고 실제 결제나 승인된 발주를 요구한다. 이는 가격 최적화가 아니라 지불 행동 확인이다. 매주 한두 개 인수 카드를 제공하며, 훅 없이 선별된 문서/PR/데모만 사용한다. 대금은 승인된 별도 실험에서만 받는다.
4. **진행 조건:** 최소 3팀 결제, 그중 2팀이 다음 기간 갱신, 중앙값 인수 준비시간 30% 이상 감소, 작성자 정정시간 10분 이하/카드, 근거 없는 승인·완료 단정 0건을 임시 gate로 둔다. 작은 표본이므로 시장 수요 추정에 쓰지 않는다. 미확인 표시는 정답을 회피하는 용도로 남발하지 않도록 승인자가 실제로 결정했는지도 본다.
5. **포기·전환 조건:** 두 차례 메시지/대상 조정 후에도 6팀 중 유료팀 2개 미만이거나 반복 사용이 없으면 제품 구현을 보류한다. 카드가 좋지만 모든 가치가 수작업 정리에서 나오면 서비스로 유지하거나 기존 PMS 템플릿/확장으로 좁힌다. 민감자료 없이는 가치가 없고 공유를 거부하면 수집 플랫폼을 만들지 않는다.
6. **그 다음 설치 실험:** 유료 반복 사용팀에게만 자동 수집이 절약할 시간을 설명하고 명확한 수집 범위를 보여준다. 실제 설치 완료·비활성화·정정·누락률을 관찰한다. 카드 수요와 훅 수요는 별도 가설이다. 무료 시연 수락이나 '설치해도 괜찮다'라는 말로 설치 장벽이 검증됐다고 하지 않는다.

## 공통 공개 실무 근거 보강

부모가 원문 확인 후 동일하게 배포한 `public-discussions.md`도 검토했다. 아래는 이 분석가가 새로 인터뷰한 내용이 아니며, 제품 도입을 입증하는 근거로 쓰지 않는다.

- [Thoughtworks 2026년 2월 retreat 보고서](https://www.thoughtworks.com/content/dam/thoughtworks/documents/report/tw_future%20_of_software_development_retreat_%20key_takeaways.pdf)의 감독·결정 처리량, 역할 간 공통 이해, 미래/현재/과거 작업 기록 논의는 '진행 대시보드'보다 '검토자가 판단할 수 있는 정보'에 초점을 두는 후보를 뒷받침한다. 공급사 주최 전문가 논의이며 독립 수요 조사 아님. Chatham House Rule에 따라 익명 의견을 유명 참가자에게 귀속하지 않는다. 행사일 2026-02-01~03, 부모 원문 확인일 2026-09-30.
- [Joshi·Parsons·Fowler 공개 대담](https://martinfowler.com/articles/convo-what-how.html)(2026-01-21)은 요구와 구현이 반복적으로 서로를 바꾼다는 관점을 제공한다. 그러므로 카드가 '처음 계획을 벗어나면 실패'라고 판단해서는 안 된다. 합당한 학습으로 바뀐 것인지, 누가 승인해야 하는지 보이게 하는 것이 더 적절하다는 분석가 추론이다. 자연어 spec의 존재만으로 공통 이해가 확보된다고 가정하지 않는다.

이 보강은 초기 결론의 확신도를 수요 검증 수준으로 높이지 않는다. 여전히 유료 반복 사용과 기존 도구 대비 실측이 필요하다.
