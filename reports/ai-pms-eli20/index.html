전체 계획을 비교하는 WBS와 Gantt

사람을 선택하면 프로젝트 목표에서 전체 Phase와 최종 완료 확인까지 이어진 흐름이 먼저 보입니다. 완료한 단계와 남은 단계를 비교하고, 단계를 누르면 바로 아래에서 담당 작업·완료 조건·막힘과 다음 행동·검사 근거를 확인합니다. 세션과 훅 로그는 이 계획의 근거를 확인할 때 펼칩니다.

Phase 연결은 계획에 선언한 순서입니다. 실제 선행 작업은 상세의 의존성으로 확인합니다. 모든 Phase가 완료되어도 프로젝트 전체 검사와 인수 조건이 남으면 최종 완료로 표시하지 않습니다. 계층형 WBS의 작업과 담당자를 타임라인 막대와 나란히 봅니다. 공개 Gantt 날짜는 명시적으로 작성한 가상 계획이며 실제 훅 로그에서 얻은 납기가 아닙니다. 일정 없는 프로젝트는 Phase 기준으로 표시합니다.

완료 기준과 검증

완료 기준은 성공 조건입니다. 검증은 특정 버전의 결과물을 그 조건으로 검사한 기록입니다. 하위 작업 검사와 전체 프로젝트 검사는 적용 범위가 다릅니다.

무엇이 어떤 역할을 하나요?

① 사용자 환경 · Harness Kit

사용자는 자신의 환경에서 목표·계획·문서·구현 결과·검사 기록을 만듭니다. Kit의 계획·결과 형식은 이 정보를 구조화하는 기반입니다.

② 중앙 프로젝트 모델

이번 구현은 로컬로 가져온 기록과 프로젝트 설명을 읽습니다. 명시된 출처 연결을 따라 여러 세션·환경을 묶고, 문서 변화와 완료 상태를 계산합니다.

③ 대시보드

사용자별 프로젝트 현황을 비교하고 목표에서 문서·단계·검증·세션으로 내려갑니다. 관리자는 검사 명령과 대상 버전, 기록의 근거를 확인할 수 있습니다.

공개 Vercel 앱은 합성 샘플을 탐색하는 정적 대시보드입니다. 별도의 선택 실행형 중앙 서비스와 송신기는 PC에서 중앙으로 연결하며 개별 훅 기록과 관리 변경을 영속 저장·집계하고 화면 갱신으로 이어줍니다. PC의 위치를 미리 알 필요는 없습니다. 실제 앱 훅 호출과 원격 두 환경 전달은 별도 실증하며, 합성 로컬 실행을 실제 사용자 수집으로 표현하지 않습니다.

사람에서 시작해 세 가지 완료를 구별합니다

사람을 선택하면 여러 환경과 프로젝트에 걸친 세션과 각 세션이 시작한 목표를 봅니다. 그 목표에 연결된 Phase·작업에서 계획과 검사·문서 근거로 내려갑니다. 세션이 종료됐다는 사실, 연결된 작업이 현재 기준으로 검증됐다는 사실, 회사나 팀의 실제 지표가 좋아졌다는 사실은 서로 다릅니다.

실행 생명주기

시작·활동·종료를 관측합니다. Stop은 턴 종료입니다. 종료된 세션도 목표 검사가 실패했을 수 있고 종료 기록을 못 받았다면 종료 불명입니다.

목표 검증과 인수

현재 산출물·작업·검사·필요한 검토를 확인합니다. 인수 선언은 목표와 검증 근거 해시에 묶이므로 파일이나 검사 기준 변경 뒤 예전 인수가 되살아나지 않습니다. 사람 판단은 선언 기록이며 외부 서명 인증이 아닙니다.

회사·팀 북극성

지표의 단위·기간·기준값·목표값과 실측을 비교합니다. 세션 목표의 기여 제안과 연결 확인을 구별합니다. 연결 확인도 인과 관계나 기여율 증명은 아니며, 개인 목표는 조직 목표와 연결 없이 유지할 수 있습니다.

로컬 기록 → 송신 대기 → 중앙 저장·집계 → 화면 적용도 구별해야 합니다. 기록기가 오류 때 에이전트를 막지 않도록 exit 0을 반환하더라도 기록 성공은 아닙니다. Kit health 상태와 중앙 capture 상태에서 마지막 기록·오류·오래된 관측을 확인합니다. 활동이 없다는 이유로 네트워크 장애나 개인 생산성 저하를 추측하지 않습니다.

연결된 화면은 cursor로 2초마다 변경을 조회합니다. JSON을 써도 각 이벤트 ID와 관리 레코드 개정이 따로 추적되면 증분 갱신이 가능합니다. 현재 자체 호스팅 런타임은 인증된 조회·내구 저장·재전송·충돌 표시를 제공하는 bounded pilot이며 대규모 운영 성능을 실증한 서비스는 아닙니다. 실행 안내와 확인 범위를 참고하세요.

완료를 판정하는 규칙

프로젝트 전체 완료 기준으로 지정한 검사가 현재 결과물 버전에서 모두 통과하면 완료 — 설정된 기준 충족으로 표시합니다. 단계 검사는 해당 단계의 완료를 보여줍니다. 전체 기준이 없거나 결과가 빠졌으면 완료를 추측하지 않습니다.

검사 후 버전이 변경되면 예전 완료 이력은 남기고 현재 상태를 재검증 필요로 표시합니다. 기준 자체가 바뀌어도 이전 검사 결과를 그대로 재사용하지 않도록 기준의 식별값을 연결합니다. 기준 정의를 교체한 뒤 옛 기준의 완료 이력을 확인하려면 변경 전 snapshot도 보관해야 합니다. 미래 시각이나 상충하는 검사 기록은 정상 완료로 승격하지 않습니다.

가져온 검사 기록은 화면을 열면서 다시 실행한 검사가 아닙니다. 대시보드는 기록의 출처와 적용 범위를 보여주며, 합성 데이터는 합성으로 표시합니다. 신뢰할 수 있는 자동 수집과 실환경 증명은 이후 연결 단계에서 다룹니다.

MCP와 데이터 소스는 어떻게 연결하나요?

MCP는 에이전트가 외부 도구를 호출하는 공통 연결 방식입니다. 데이터 소스는 그 도구가 참조하는 문서·저장소·데이터베이스·API입니다. 서버 별칭이 같아도 다른 사람의 환경에서는 다른 데이터베이스일 수 있습니다.

① 설정 · 선언

연결을 설정했다는 기록은 사용할 수 있는 후보를 알려줍니다. 실제로 호출하거나 데이터를 읽었다는 뜻은 아닙니다.

② 호출 · 관측

훅이 제공한 서버·도구 이름, 요청·성공·실패, 제공된 실행 시간을 기록합니다. 서버의 성공 응답이 내부 데이터베이스 접근까지 증명하지는 않습니다.

③ 참조 · 근거

명시적으로 노출된 논리 데이터 ID와 입력·출력·선언 구분을 저장합니다. 문서 활용은 명시적인 산출물 참조가 있을 때만 연결합니다.

대시보드에서는 프로젝트 → 사용자·환경·세션 → MCP 서버·도구 → 데이터 참조 → 산출물 참조로 내려갑니다. 관리자는 같은 의존성을 가진 프로젝트, 실패가 나온 세션, 출처가 불명확한 참조를 찾아 추가 검증이나 작업 재개를 요청할 수 있습니다. 호출 횟수로 사람의 생산성이나 솔루션 품질을 평가하지 않습니다.

기록기는 도구 입력·응답 원문, SQL, 자격 증명과 파일 경로를 저장하지 않습니다. 검토한 로컬 매핑은 선언으로 표시하고, 훅이 제공하지 않은 내부 데이터 접근은 미관측으로 남깁니다. 현재 기록기는 Codex·Claude의 명령 훅 형식을 지원합니다. Cursor·Gemini 어댑터와 각 앱에서의 실제 훅 전달 검증은 후속 범위입니다.

회사 목표를 개인의 작업까지 연결합니다

회사는 “고객 요청 처리 시간을 줄이자”라는 결과 목표를 맡길 수도 있고 “요청 분류 화면을 만들어라”라는 작업을 지시할 수도 있습니다. 전자는 담당자가 구현 방법을 정하고, 후자는 지정한 작업을 수행합니다. PMS는 목표의 원문과 버전, 위임한 사람·담당자·성공 조건을 프로젝트에 연결합니다. 독립적인 개인 프로젝트에는 회사 목표를 요구하지 않습니다.

목표 · 위임

회사 또는 개인이 달성하려는 결과와 담당자의 책임을 명시합니다.

계획 · 테스트 설계

어떤 요구사항을 왜 검사하는지, 계획과 기준이 어떻게 개정됐는지 남깁니다.

실행 · 결과물

실패·수정·재검증을 실행 환경과 정확한 대상 파일 버전에 연결합니다.

예를 들어 화면 테스트가 통과하면 그 기술 조건은 충족한 것입니다. 실제 고객 요청 처리 시간이 줄었는지는 별도의 업무 결과가 필요합니다. 현재 화면에서는 업무 성과 미관측으로 표시합니다. 기술 조건 통과를 회사 목표 달성으로 바꾸지 않습니다.

사람이 맡은 작업을 기준으로 진행을 읽습니다

한 사람이 여러 프로젝트를 맡고 여러 사람이 하나의 프로젝트를 함께 만들 수 있습니다. 사람을 선택하면 그 사람의 프로젝트 목적과 책임 작업을 봅니다. 프로젝트 전체 현황과 선택한 사람의 담당 작업 수는 따로 표시합니다.

Phase · 계획

목표를 구현 단계로 나누고 각 단계에 담당자·선행 작업·완료 조건을 가진 작은 작업을 연결합니다.

작업 · 검증

작업의 인수 검사와 현재 파일 버전을 확인합니다. 선행 작업이나 필요한 사람 승인이 남으면 완료로 닫지 않습니다.

관리 · 판단

검증 실패, 기준 누락, 선행 작업 대기, 사람 검토 요청을 담당자와 다음 행동으로 보여줍니다.

가상 사례로 필수 작업 10개 중 6개 완료, 1개 검증 실패, 1개 검토 대기, 2개 착수 가능이면 관리자는 실패 지원과 검토 결정을 먼저 처리할 수 있습니다. 6/10은 작업 수 기준이며 업무 성과 60%나 노력 60%라는 뜻은 아닙니다. MCP와 세션 기록은 관련 작업을 펼쳤을 때 원인과 근거로 확인합니다.

현재 계획·검사 기준·파일이 바뀌면 과거 검증과 승인을 재검토합니다. 작업이 빠진 Phase나 단계 종료 조건이 없는 Phase는 완료로 닫지 않습니다. 자세한 입력은 JSON 필드 설명과 작업 관리 안내에서 확인하세요.

테스트가 만들어진 이유와 실제 실행을 구분합니다

검사 기준은 “무엇을 만족해야 하는가”, 테스트 계획은 “어떤 요구사항을 어떤 방법으로 왜 검사하는가”입니다. 에이전트는 기존 요구사항·Handoff 계획에서 명시적 이유와 적용 범위를 연결합니다. 로컬 runner는 계획된 명령을 실행하고 시작·종료 시각, 종료 코드, 담당 사용자·환경, 계획 해시, 검사 대상 파일들의 해시를 기록합니다. 명령의 전체 출력은 수집하지 않습니다.

Handoff 결과에 적힌 통과는 선언 근거입니다. runner가 관측한 실행과 구분하고 현재 완료 판정에 사용하지 않습니다. 실행 영수증도 암호학적으로 신뢰된 외부 증명이 아니라 로컬 실행 기록입니다. 파일 해시는 동일성 확인이며 보고자의 정직성을 보증하지 않습니다.

실패 → 수정 → 통과가 여러 시도로 남습니다. 코드나 테스트 기준이 바뀌면 이전 통과 이력은 유지하고 재검증을 요구합니다. 파일 manifest는 사용자가 지정한 범위이므로 모든 관련 파일을 빠짐없이 포함했는지도 검토해야 합니다.

중앙 관리자는 무엇을 할 수 있나요?

도움 배정

어떤 검사에서 막혔는지, 확인된 원인인지 가설인지, 다음 조치와 도움 담당자를 확인합니다. 활동이 적다는 이유로 막힘을 추정하지 않습니다.

검증 누락 보완

요구사항에 연결되지 않은 검사, 미검증 환경, 오래된 통과를 찾아 재검증이나 기준 보완을 요청합니다.

Kit 개선 시험

철칙·하네스·검증 루프·스킬·MCP 개선 가설과 변경 버전, 개선 전후 실행 근거를 비교합니다.

세션 수·토큰 수·테스트 수는 개인 생산성 점수가 아닙니다. 공통 운영 규칙의 효과도 개선 후 조건이 같은 재실행 근거가 있어야 판단할 수 있습니다. 대시보드는 근거와 미관측 부분을 함께 보여줍니다.

Graphify는 선택적인 구조 분석입니다

Graphify는 코드에서 파일·함수의 구조와 관계를 분석합니다. 변경의 영향 범위와 관련 테스트 후보를 찾는 데 도움이 됩니다. 목표 달성·실제 실행 경로·테스트 커버리지를 자동 증명하지는 않습니다.

필요한 프로젝트에 한해 code-only 분석을 훅이나 명시적 명령으로 실행할 수 있습니다. 생성기 버전, 대상 소스 해시, 생성 시각, 성공 여부와 최신성을 기록합니다. 현재 코드와 해시가 다르면 오래된 그래프입니다. 홈 전체 분석이나 전역 훅을 설치하지 않으며, 선택 분석 실패로 본래 검증을 막지 않습니다.

변경 이유와 에이전트 인계도 추적합니다

변경 체크포인트는 세션·에이전트와 Git 커밋·미커밋 변경 해시, 현재 산출물 및 검사 시도를 연결합니다. Git 정보는 로컬 읽기 관측이며 기여 세션은 명시적 선언입니다. 검사 연결은 지정 manifest의 동일성으로, 전체 Git tree의 검사 증명은 아닙니다.

판단 기록은 검토한 대안·선택 이유·원문 요구사항과 이전 판단을 대체한 관계를 보존합니다. 세션 인계는 전달 패킷 해시와 요구사항·판단·실패 검사를 이어주고 실제 활용은 미관측·선언·조회 근거 관측으로 구분합니다. 패킷 생성만으로 다음 에이전트가 읽었다고 판단하지 않습니다.

기록 상태는 사용자·환경·도구별 지원 항목, 마지막 관측, 중지·오류·미지원 사유를 표시합니다. 가져온 당시의 상태 보고이며 실시간 접속 상태나 개인 생산성 지표가 아닙니다. 상세의 변경 · 판단 · 인계 · 기록 상태 탭에서 확인하세요.

어떻게 사용하나요?

미리 생성된 대시보드 파일을 브라우저에서 열면 됩니다. 프로젝트 검색과 사용자·단계·상태·MCP·데이터 소스 필터로 범위를 좁히고 상세에서 문서, 검사, 세션, MCP·데이터 참조, 원본 근거를 확인합니다. 다른 정규화된 snapshot JSON을 파일로 가져오거나 붙여넣고, 현재 snapshot을 내보낼 수도 있습니다.

새 자료로 화면을 생성하려면 기존 중앙 저장 JSON과 로컬 프로젝트 catalog를 사용합니다. v3 catalog에는 환경 간 프로젝트 연결, 문서, 목표·위임·계획·테스트 시도·막힘·개선 근거를 넣습니다. Kit의 management_recorder.py가 로컬 검사 영수증을 만들고, 중앙 생성기는 그 파일을 읽어 화면을 만듭니다. 원격 API를 호출하거나 검사 명령을 실행하지 않습니다. 구체적인 입력 예제와 명령은 구현 안내에 있습니다.

검증 근거와 남은 범위

실제 검증 내역은 대시보드 인수 기록과 브라우저 관측에서 확인합니다. 합성 사용자·세션으로 로컬 프로젝트 연결과 완료 판정, 화면 동작을 검증하며 실제 여러 PC에서 자동으로 도착한 데이터라고 표현하지 않습니다.

기반 근거: 사용자 목적 보충, 이번 구현 명세. Kit의 계획에는 goal·phases·검증 기준이, 결과에는 검사 명령·종료 코드가 있습니다. 작업 검증기는 로컬 입력과 중앙 투영에 재사용됩니다. 사람·세션 모델 및 선택 실행형 동기화는 최신 명세와 실행 안내를 기준으로 합니다. 이전 브라우저 기록은 새 화면의 현재 검증을 대체하지 않습니다.
