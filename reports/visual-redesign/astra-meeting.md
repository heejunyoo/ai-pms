> Astra의 구현 전 설계 제안입니다. 파일 작성 뒤 사용량 한도로 응답이 중단되었습니다. 현재 코드의 최종 승인이나 실제 브라우저 인수 결과가 아닙니다.

# AI PMS 시각화·IA 전문가 미팅

기본 화면은 **사람별 프로젝트 목록 → 목표와 전체 WBS 계획 → 한 작업의 다음 행동**으로 고정하고, 큰 Phase 카드 대신 **계층과 상태가 한눈에 맞춰지는 작업표**를 중심 시각화로 채택합니다. 세션·검증·MCP 원본은 작업에 연결된 근거로 보존합니다.

2026-10-04. 사용자 요청 “흐름 뿐 아니라, 시각화 표현도 더 직관적 이어야해. Astra 통한 전문가 미팅, handoff 로 액션 수행하고 보고 할것.”에 대한 AI 전문가 관점 검토입니다. 실제 사람 인터뷰나 서로 독립적인 복수 전문가의 실증 합의가 아닙니다. 아래 관점 토론은 한 분석 에이전트가 구성했습니다. 코드·문서 확인과 디자인 제안을 구분하며, 실제 브라우저를 보지 않았으므로 미적 완성도·실사용 이해도는 미검증입니다. 모바일 인수는 사용자 요청대로 이번 필수 범위에서 제외합니다.

## 3. 권장 IA와 구체 화면

### A. 사람별 프로젝트 목록

상단은 `프로젝트`, `판단 필요`, `팀 목표` 정도의 짧은 전역 탐색과 사람 선택을 제공합니다. 팀 목표의 실제 관측과 기여 확인 기능은 숨김 CSS로 제거하지 않습니다. 현재 데이터가 없으면 빈 상태로 보존합니다. 개인 프로젝트에 회사 목표 연결을 강제하지 않습니다.

프로젝트를 큰 카드 격자로 쌓지 않고 같은 열의 행으로 비교합니다. 각 행은 프로젝트 이름과 한 문장 목표, 참여자, 현재 단계 이름, 상태/다음 행동 요약을 표시합니다. 단계 수 요약은 보조 정보이며 프로젝트별 목표 달성률로 환산하지 않습니다. `API/MCP`는 프로젝트 내부 기본 화면에서 확인할 수 있어야 하고 목록의 필수 열까지 늘리지 않습니다. 프로젝트/목표 검색과 사람 선택을 기본 필터로 남기고 기술 필터는 근거 쪽에 둡니다.

사람 선택은 ‘그 사람의 참여 범위’입니다. 공동 프로젝트가 개인 프로젝트처럼 바뀌거나, 다른 사람의 선행 작업과 막힘이 계획에서 사라지면 실패입니다. 선택한 사람의 담당 작업에는 작은 표식을 추가할 수 있습니다. 사람별 `세션 이력`은 바로 접근 가능한 보조 링크로 남깁니다.

### B. 프로젝트 계획: 전체와 현재를 같은 공간에

상단: 목표, 참여자, 문서/현재 검증 기준, 마지막 관측. 그 아래 ‘지금 확인할 것’ 한 줄과 전체 WBS를 보여줍니다. 긴 출처 경로·해시·기록 ID는 기본 화면에 노출하지 않습니다.

```text
프로젝트 이름                       참여 Alice · Bob
목표: …                             기준: 현재 검증 / 문서 기록 날짜
지금 확인: Bob이 중복 정책 확정 → 작업 보기

전체 계획                        담당      상태           다음 행동
✓ 01 요구사항                    Alice     달성           작업 2/2
▾ 02 구현                        공동      진행 중        작업 1/3
    ✓ 2.1 입력 연결              Alice     달성
    ! 2.2 중복 정책              Bob       확인 필요      정책 선택 →
    ○ 2.3 통합                   Alice     대기           2.2 완료 후
▸ 03 검증                        Alice     예정           작업 0/2
◇ 최종 인수                                미확인         완료 조건 보기 →

모든 작업 펼치기       참고한 API · MCP       근거와 기록
```

위 내용은 배치 예시이며 실제 프로젝트 사실을 뜻하지 않습니다. `2.2 완료 후` 같은 의존성은 입력에 명시된 경우에만 표시합니다. Phase 순서에 화살표를 붙여 의존성을 암시하지 않습니다. 모든 Phase와 최종 인수는 접힌 상태에서도 존재와 이름이 보이고, 작업이 하나도 없으면 `작업 계획 미입력`을 표시합니다.

시각 규칙:

- 한 행의 같은 위치에 단계/작업 이름, 담당, 상태를 정렬합니다. Phase 행만 조금 굵게 하고 작업은 들여쓰기로 소속을 표현합니다. 카드마다 테두리를 두르지 않습니다.
- `✓ 달성`, `● 진행 중`, `! 확인 필요`, `○ 예정`, `? 미확인`, `◇ 최종 인수`처럼 기호와 문자를 함께 사용합니다. 재검증 필요·검사 실패·검토 대기는 기존 판정 의미를 그대로 이름으로 표시합니다.
- 파랑은 현재 선택·진행, 녹색은 달성, 호박색은 판단 필요에 제한합니다. 색만으로 의미를 전달하지 않습니다. 단순 ‘완료/미완료’ 두 상태로 압축하지 않습니다.
- 현재 단계가 병렬이면 복수의 진행 상태를 보여줍니다. 단 하나의 커서나 “다음 단계”를 억지로 고르지 않습니다.
- 계획 순서와 시간축을 구분합니다. 실제 시작/종료 예정일이 없는 항목에는 길이로 기간을 암시하는 Gantt 막대를 만들지 않습니다. 명시적 날짜가 있는 경우만 별도 일정 보기로 전환합니다.
- 작업 수가 많을 때는 Phase를 접어 스캔하고 전체 펼치기·목표/작업 검색으로 찾습니다. 전체 WBS가 분석 근거에만 존재하는 상태로 되돌리지 않습니다.

### C. 작업/Phase 상세

작업 상세는 별도 주소를 유지하며 `지금 할 일 → 담당·요청 대상 → 막힌 구체 이유 → 완료 조건` 순으로 보여줍니다. 관련 API/MCP와 현재 결과/검증은 짧게 연결하고 원시 로그는 접습니다. 완료된 작업은 다음 행동을 창작하지 않고 결과와 충족 조건을 보여줍니다.

Phase 상세에는 목표, 상태, 해당 Phase의 **전체 작업**을 표시합니다. 완료 작업도 수동 펼침으로 확인 가능해야 합니다. 현재처럼 작업 목록을 지우고 목표·상태만 보여주면 인수 실패입니다. 목록 → 프로젝트 → 작업은 최대 두 번의 선택으로 도달하고 뒤로 가기/새로고침/직접 링크가 동일한 범위를 복원해야 합니다.

### D. 근거: 9탭을 없애도 증거는 잃지 않습니다

기본 화면에는 9개 종류를 고르는 메뉴를 두지 않습니다. `근거와 기록` 안에서 다음 세 질문으로 묶되 기존 상세 렌더·원본 데이터는 보존합니다.

| 사용자 질문 | 유지할 기존 근거 |
|---|---|
| 왜 이 상태인가? | 작업 판정, Phase/프로젝트 검증, 검사 계획·시도·승인 |
| 어떻게 바뀌었는가? | 목표/범위 변경, 결정·인계, 세션·환경, 기록 상태 |
| 무엇을 참고했는가? | 문서, API/MCP/데이터 연결, 출처 |

세 묶음이 새로운 대형 탭 세 개로 정보 이동만 반복하면 실패입니다. 작업과 Phase에서 해당 범위로 바로 진입하고, 프로젝트 전체 근거는 필요한 사람만 확장합니다. 기존 근거 항목의 도달 경로를 매핑한 회귀표로 보존 여부를 확인해야 합니다.

## 4. 세션을 관리하는 이유와 합치면 안 되는 경우

세션은 **목표를 달성하려고 실제로 수행한 실행 단위**입니다. 같은 프로젝트에 여러 세션이 생기는 이유는 구현·검증·재시도·다른 사람의 작업이 이어지기 때문입니다. 세션 수 자체는 성과가 아니며 모든 세션을 별도 목표 프로젝트로 만들 필요가 없습니다.

기본 계획에는 `연결된 세션 N개` 정도만 보조로 제공하고, 조회 시 한 세션당 하나의 의미 있는 항목을 보여줍니다: 사람·시점·목표·연결 작업·실행 상태·목표 확인 상태. 세션 종료와 목표 인수는 별도 열/라벨로 남깁니다. 원시 이벤트 수·환경 ID는 그 항목의 근거에 둡니다. 사람별 세션 화면은 프로젝트를 가로질러 이 항목들을 보여줄 수 있어야 합니다.

원시 `p.sessions`와 `operations.sessions`를 같은 이름/목표 문장으로 합치지 않습니다. 확인된 actor/environment/session/source identity 또는 기존 명시 연결로만 하나의 뷰에 연결하고, 연결되지 않은 기록은 `목표 연결 미확인`으로 별도 표시합니다. 한 세션이 여러 작업/Phase를 다루는 다대다 관계도 유지합니다. 목표 문장이 비슷하다는 이유로 자동 분류·병합하지 않습니다. 의미 분류/목표 중복 추천은 추후 모델 분석 범위이며 이번 UI 작업에서 가짜 분석 결과를 만들지 않습니다.

## 5. 추천안을 깨보는 반례

총 9개 반례로 검토했습니다. 다음은 구현 인수에 그대로 넣을 사례입니다.

| 반례 | 단순 대안의 실패 | 추천안의 처리 |
|---|---|---|
| 2/3 Phase 완료지만 마지막 Phase가 전체 노력의 대부분 | 진행 막대 67%가 시간/성과 67%처럼 읽힘 | ‘2/3 단계 달성’이라고 분모 의미를 명시하고 남은 Phase 이름·작업 노출. 전체 목표 % 생성 금지. |
| Phase 12개, 작업 80개 | 거대한 카드가 길어져 전체 위치 상실 | Phase 행은 전부 표시, 현재/막힘 확장, 전체 펼치기·찾기. 긴 페이지에 원시 로그를 덧붙이지 않음. |
| 개발과 문서가 동시에 진행 | 단일 단계 커서·순서 화살표가 허위 직렬 관계 생성 | 복수 진행 상태, 실제 선언된 선행 작업만 표시. |
| 날짜 없는 계획 | Gantt 길이와 x축이 허위 일정 생성 | 계층 작업표를 기본으로, 일정 미입력 상태 유지. |
| Bob을 선택했는데 Alice의 선행 작업 때문에 막힘 | 개인 필터가 의존 관계를 숨김 | 공동 계획 전체 유지, Bob 책임 표시와 Alice 의존 작업을 함께 제공. |
| 모든 세션 종료, 검사 실패 또는 목표 미입력 | 세션 종료=프로젝트 완료로 오해 | 실행 상태와 목표 상태 분리, 기존 완료 계산 보존. |
| 문서에는 완료지만 현재 검사가 없음/오래됨 | 녹색 체크가 현재 검증 완료로 오해 | 문서 근거와 날짜를 표시, 최종 인수 미확인 유지. |
| MCP는 설정만 되었거나 Phase 연결이 없음 | 도구 로고가 실제 사용/기여처럼 보임 | 설정·입력/호출 관측을 구분, Phase에 임의 귀속 금지. |
| 작업 테스트 통과지만 팀 북극성 실적은 없음 | 기술 완료를 사업 지표 달성으로 환산 | 팀 목표 별도 경로와 관측 근거 유지. 개인 목표는 미연결 허용. |

선택지 간 임의 가중 점수는 사용하지 않았습니다. 순수 진행 막대는 전체 작업과 막힘 관계를 표현하지 못하고, 카드 격자는 비교 기준 정렬과 대규모 계획에 불리합니다. 노드 그래프는 실제 복잡한 의존성이 주질문일 때만 추가할 가치가 있습니다. 현재 사용자 질문은 목표·계획·진척·참고 자원이므로 계층 작업표가 가장 적은 시각 문법으로 답합니다. 이는 디자인 가설이며 실제 사용자 과제에서 실패하면 조정합니다.

## 6. 실행 가능한 handoff 범위

부모가 구현 정본·소유 파일·현재 판정 불변조건을 고정한 뒤 다음 패킷을 발행하는 것이 적합합니다. 이 보고서는 실행 계획 승인이나 구현 완료 영수증을 대신하지 않습니다.

| 순서 | 패킷 | 결과와 경계 |
|---|---|---|
| 1 | 기본 IA·WBS 투영 | `human-view.js/css`의 기본 목록·계획·Phase 상세를 개편하고 정본 생성 경로에서 `dashboard.html` 갱신. 모든 Phase/작업·담당·상태·최종 조건, API/MCP 접근 보장. 기존 계산/입력 계약 변경 없음. |
| 2 | 세션·근거 접근 정리 | 원시/목표 세션의 중복 렌더 해소, 검증 가능한 identity만 연결. 사람별 세션·팀 목표 경로 복원. 기존 9개 근거 기능의 새 도달 경로 표와 회귀 검사. 1과 공유 렌더 지점이 많으므로 병렬 수정하지 않음. |
| 3 | 데이터 반례 + 데스크톱 브라우저 인수 | 합성 공동 프로젝트와 실제 비공개 프로젝트의 문서 기준 상태를 각각 확인. 직접 링크/뒤로/새로고침/키보드/증분 갱신·포커스 확인. 실제 사용자에게 보이는 결과를 보고 최종 판정. |

당장 하지 않을 범위: 새 DB/API 계약, 새 외부 API, 의미 기반 자동 분류/중복 병합, provider trust/원격 두 사용자 인수, 배포. 이런 작업이 필요하면 별도 승인·패킷 경계를 사용합니다. 사용자 모바일 제외 결정을 되돌리지 않습니다. 공개 샘플과 실제 비공개 프로젝트의 데이터 분리도 유지합니다.

## 7. 최종 인수 기준

1. 처음 보는 검토자가 한 프로젝트 화면에서 목표, 모든 Phase의 존재, 현재 진행/확인 필요, 남은 작업과 최종 인수를 구분할 수 있습니다. ‘어떤 단계인가’를 알아내기 위해 hover나 근거 탭이 필요하지 않습니다.
2. 현재/막힘 작업이 기본으로 보이고 전체 원자 WBS가 한 번의 펼침으로 나옵니다. Phase 상세에서 완료/남은 작업과 담당자를 확인할 수 있습니다.
3. 사람 선택 후 두 개 이상의 프로젝트 및 공동 프로젝트를 조회하며, 다른 담당자의 선행 작업이 사라지지 않습니다. 사람별 세션과 팀 목표도 실제 접근할 수 있습니다.
4. 단계 목표·참고 API/MCP·달성 상태·다음 행동이 각각 어떤 데이터와 근거에서 왔는지 추적됩니다. unknown, 문서상 완료, 현재 검증, 최종 인수는 구별됩니다.
5. 동일 세션이 원시 목록과 목표 목록에 이중 나열되지 않습니다. 연결 미확인 기록은 버리지 않고 남기며, 종료 세션의 목표 미달성 반례가 유지됩니다.
6. 기존 9개 근거 종류의 기능을 새 경로에서 모두 찾을 수 있습니다. 최종 완료 계산·기존 검사·계약은 회귀 없이 유지됩니다.
7. 데스크톱 브라우저에서 목록→계획→작업→근거→복귀, history/reload, 키보드 선택, 증분 상태 변경을 직접 실행합니다. 작은 브라우저 창과 긴 제목·12개 Phase에도 주요 정보가 잘리거나 겹치지 않는지 관찰합니다. 화면 캡처와 관찰 기록은 현재 빌드와 연결합니다.
8. 브라우저가 불가능하면 `implementation_verified`와 `desktop_visual_verified=false`를 구분해 보고합니다. DOM/소스/스크린샷 없는 바이트 일치만으로 시각적 완료라고 하지 않습니다. 모바일은 이번 필수 인수 아님을 명시합니다.

자가검토: 분해의 네 축은 질문 순서로 나누었습니다. 하나의 검증 데이터가 계획 상태와 근거에 함께 쓰여도 기본 위치는 역할별로 다르므로 원시 내용을 중복 나열하지 않습니다. 사람·공동 목표·세션·팀 기여·API/MCP·누락/지연을 누락하지 않았고, 화면 수준과 데이터 수준을 같은 탐색 층위로 섞지 않았습니다. 사실 확인은 소스/문서 범위이며 UX 효과와 시각 품질은 실제 브라우저 인수를 기다립니다.
