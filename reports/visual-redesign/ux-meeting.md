# AI PMS 시각 재설계 — 제품·정보 디자인 검토

검토일: 2026-10-04. 이 문서는 AI 전문가 미팅에 제출하는 한 관점의 설계안입니다. 외부 전문가 인터뷰나 실제 사용성 평가 결과가 아닙니다. 현재 소스와 목적 문서를 대조했습니다. 화면 렌더를 관찰하지 않았으므로 가독성·시각 품질 PASS를 판정하지 않습니다. 모바일은 이번 인수 범위에서 제외합니다.

## 제안의 중심

**공동 프로젝트의 전체 계획을 정렬된 WBS 작업표로 먼저 보여주고, 오른쪽 축에서 완료·현재·남은 단계를 함께 읽게 합니다.** 사람 선택은 그 사람의 책임을 강조하되 다른 참여자의 단계와 최종 완료 조건을 지우지 않습니다. 막힌 행을 누르면 별도 상세 주소에서 원인·담당·다음 행동을 읽습니다. 기본 화면의 분석 근거 목록과 9개 탭은 없애고, 각 질문에서 해당 근거로 직접 내려갑니다.

한 프로젝트의 상태를 01→02→03 카드로 표현하는 것만으로는 목표·작업·담당·최종 인수의 관계를 읽을 수 없습니다. 필요한 것은 장식적인 그래프가 아니라 같은 행에서 이름, 책임, 상태, 계획상 위치를 비교할 수 있는 시각 규칙입니다.

## 목적과 근거

정본은 `PRODUCT-INTENT.md`입니다. 다수 사람의 다수 환경에서 기록을 모으는 중앙 관리 제품이며, 개인 계획 도구나 하나의 중앙 실행기로 축소하지 않습니다. 사람→참여 공동 프로젝트→전체 Phase/작업→상세를 유지합니다. 사람의 세션 목표와 정상 종료, 회사·팀 목표의 확인된 기여 역시 사라지면 안 됩니다. 개인 목표는 조직에 연결하지 않아도 됩니다.

확인한 근거:

- `PRODUCT-INTENT.md`: 중앙 관리, 사람·세션, 북극성, WBS/Gantt, 별도 상세 페이지, 최소 기본 정보의 후속 정정.
- `NEXT_SESSION.md` 최신 두 섹션: 현재 배포본은 데스크톱 실제 렌더·history 인수가 미완료. 기존 배포·바이트 일치가 이번 시각 품질의 증거는 아님.
- `reports/rensei-research/assessment.md` 5–8절: 계획 의존성과 실행 재시도 구분, 판단 필요의 요청·영향·근거·담당·행동, 사업 목표와 기술 검증 구분.
- `specs/ai-pms-dashboard/human-view.js`: `renderPhaseFlow`, `renderShared`, `renderDetail`, `humanRenderSessions`, `renderTab`의 재정의.
- `specs/ai-pms-dashboard/human-view.css`: `.human-phase-flow`, `.human-phase-node`, `.human-mini-node`, 숨긴 운영 영역.
- `specs/ai-pms-dashboard/dashboard.html`: 기존 WBS, 원래 `renderShared`, 원래 `renderTab`와 세션 기록 렌더.

Graphify 1500토큰 조회는 `human-view.js`와 해당 함수 위치를 확인하는 보조 수단으로 사용했습니다. 결과가 잘려 원본 함수도 직접 읽었습니다. 그래프 조회는 실행 관계나 화면 가독성을 증명하지 않습니다.

## 왜 현재 구조가 사용자의 질문에 답하지 못하는가

| 관찰한 구조 | 읽는 사람이 잃는 정보 | 바꿀 지점 |
|---|---|---|
| `renderPhaseFlow`가 WBS를 카드 목록으로 대체 | 작업 단위·담당·병렬 진행·남은 작업을 같은 축에서 비교할 수 없음 | WBS와 상태축을 기본 계획 화면으로 복원 |
| 카드 수가 6개 이상이면 CSS가 세로 목록으로 전환 | 계획 규모에 따라 시각 문법이 바뀌고 긴 화면이 됨 | 동일한 행 문법 유지, Phase 펼침으로 밀도 조절 |
| 화살표를 그리고 “선행조건이 아니다”라고 설명 | 연결선의 자연스러운 인과 해석과 텍스트 설명이 충돌 | 의존성이 없으면 연결선을 그리지 않고 순서축만 사용 |
| 카드의 5px 색 띠 | 무엇이 완료인지 색과 hover에 의존 | 상태 단어와 목표 요약, 색+기호를 함께 제공 |
| `renderShared`가 원래 담당 작업 요약을 이름 한 줄로 축소 | Alice/Bob이 같은 프로젝트인지, 누가 무엇을 맡았는지 불명확 | 하나의 프로젝트 아래 두 참여자와 각 책임 요약 표시 |
| Phase 상세가 미완료 작업 목록을 목표·상태·참조로 대체 | 이 단계의 실제 작업과 다음 행동까지 근거를 통해 돌아감 | Phase 목표 아래 원자 작업 행과 상태를 함께 표시 |
| 세션 탭에서 기본 raw표 다음에 목표·인수 목록 append | 한 세션을 두 번 해석하고 ID/환경/개수에서 의미를 찾아야 함 | 목표 중심 단일 세션 목록, raw는 선택 세션의 출처에만 |
| 9개 분야 탭을 근거 페이지에 유지 | “왜 막혔나”가 아닌 “어떤 스키마인가”를 먼저 선택 | 현재 질문에 연결된 단일 근거 상세 |
| CSS로 회사·팀/세션 영역 전체 숨김 | 최소 정보화가 제품 목적 누락으로 이어짐 | 사람 상세와 별도 회사·팀 화면으로 목적 보존 |

이는 소스로 확인한 구조적 원인입니다. 실제 글자 크기·줄바꿈·정렬·색 대비의 관측 판정은 데스크톱 렌더가 필요합니다.

## 시각 표현 컨셉: 정렬된 계획 보드

프로젝트 화면에는 목표 한 문장, 공동 참여자, 전체 계획표, 최종 완료 조건만 우선 보입니다. API/MCP는 관련 Phase를 선택했을 때 그 단계의 참조로 보여줍니다. 목록 화면에 큰 계획표를 여러 개 쌓지 않습니다.

날짜 없는 프로젝트는 오른쪽에 **단계축**을 사용합니다. 헤더도 “단계별 계획”이라고 씁니다. 칸 너비와 막대 길이는 기간·노력·ETA가 아닙니다. 승인된 일정이 있는 경우에만 날짜축 Gantt를 사용하고, 계획 일정과 실제 작업 기록을 시각적으로 구별합니다. 없는 날짜를 추정하지 않습니다.

```text
← Alice의 프로젝트                    참여자  Alice [데이터 연결]  Bob [정책 합의]
Recall 공동 구축
목표: 팀원이 자료를 등록하고 필요한 내용을 다시 찾을 수 있다.
회사·팀 기여: 팀 지식 접근 개선 · 담당자 확인  [기여 근거]

전체 계획                 완료 1단계 · 진행/막힘 2단계 · 남음 1단계
                         ※ 일정 미입력: 아래 칸은 단계 순서입니다.
단계 / 작업              담당       상태           1 정의  2 연결  3 검증  4 인수
v 1. 필요한 정보 확정     Alice      ✓ 완료          [완료]
    등록 항목 확정        Alice      ✓ 완료             ●
v 2. 데이터 연결          Alice      ! 막힘                 [막힘]
    내부 API 연결         Alice      ! 권한 확인 필요          !    [상세]
    중복 정책 합의        Bob        ▶ 진행 중                ▶    [상세]
> 3. 검색 결과 검증       Alice      ○ 예정                         [예정]
> 4. 팀 사용 확인         Bob        ○ 예정                                 [예정]
◆ 최종 완료 조건: 등록·검색 검사 + 팀 사용 확인 + 최종 인수   [조건 보기]
```

위 예시는 설계용 가상 문구이며 실제 프로젝트 상태가 아닙니다. ‘완료 1단계’는 개수 요약이며 노력 기반 완료율이나 납기 전망으로 표현하지 않습니다. 여러 단계가 병렬 진행되면 모두 ‘진행 중’으로 표현합니다. 자동으로 한 개의 현재 Phase를 고르지 않습니다.

표현 규칙:

- 왼쪽 단계명과 오른쪽 상태 셀은 동일한 행 높이와 기준선으로 정렬합니다. sticky 이름/담당 영역과 차트 안의 가로 스크롤로 관계를 보존합니다.
- Phase는 굵은 제목과 접기 기호, 작업은 들여쓰기 한 단계로 구분합니다. 들여쓰기 깊이를 늘리는 대신 더 깊은 작업은 상세에서 읽습니다.
- 완료는 녹색 체크, 진행은 파란 진행 기호, 막힘은 호박색 경고, 검사 실패는 붉은 실패 기호, 예정은 회색 빈 원, 미관측은 물음표와 단어로 구별합니다. 색만으로 상태를 전달하지 않습니다.
- 경고는 해당 행에 배치합니다. 프로젝트 위에 모든 경고를 줄줄이 반복하지 않습니다. 최종 완료는 독립된 마름모/행으로 표현합니다.
- 문서상 완료와 현재 검증 완료는 같은 녹색 표시를 공유하지 않습니다. “문서상 완료 · 현재 검증 미확인”을 행에 씁니다. 기존 판정 모델을 바꾸지 않습니다.
- 행 전체는 상세 진입점이며 버튼/링크 이름에 작업명과 상태를 포함합니다. hover 전용 정보와 좁은 막대 클릭에 의존하지 않습니다.

## 사람·공동 프로젝트·세션의 의미

한 사람은 여러 프로젝트에 참여하고, 한 프로젝트에는 여러 사람이 참여합니다. 사람은 여러 환경에서 여러 세션을 시작하며, 하나의 세션은 현재 명시된 프로젝트와 여러 작업에 연결될 수 있습니다. 현재 계약에서 세션의 프로젝트가 하나로 귀속되면 화면도 이를 존중합니다. 여러 프로젝트에 걸친 세션을 추측해서 만들지 않습니다. 이름·목표 텍스트가 비슷하다는 이유로 프로젝트를 합치지 않습니다.

사람 선택 후에도 공동 프로젝트의 ID·목표·전체 계획은 그대로입니다. 선택한 사람의 담당 작업만 표시하거나 다른 사람의 작업을 제거하면 중앙 공동 관리가 다시 개인 도구가 됩니다. 선택한 담당 행은 강조하고, 다른 담당자는 정상 대비로 남깁니다. 프로젝트 목록에는 같은 프로젝트를 두 개 복제하지 않고 ‘Alice·Bob 공동’으로 표시합니다.

```text
사람  [전체] [Alice 선택] [Bob]
Alice
참여 프로젝트 2개                                      [세션 보기]
Recall 공동 구축       Alice: 데이터 연결 / Bob: 정책 합의
현재: 연결 단계 막힘   목표: 자료 등록과 재검색             [전체 계획]
개인 자료 정리         Alice
현재: 사용 확인 중     목표: 개인 자료를 주제별로 정리      [전체 계획]
```

사람 상세에서 ‘세션 보기’를 선택하면 환경을 가로지르는 목표 중심 목록으로 갑니다. 이는 원본 로그 창이 아니라 **누가 어떤 작업을 위해 실행했고 그 결과가 어디에 연결됐는지** 확인하는 화면입니다.

```text
Alice의 세션
목표                         프로젝트/작업       실행 종료       목표 확인
내부 API 연결 확인           Recall / API 연결   종료됨          미달성
검색 입력 개선               Recall / 검색 입력  실행 중         확인 대기
각 행 선택 → 연결 Phase/작업, 이번 결과, 현재 검증, 출처
```

세션 종료와 목표 달성은 별도 열입니다. 정상 종료돼도 목표 검증이 없으면 ‘달성’으로 바꾸지 않습니다. 목표 미입력은 ‘목표 미입력’, 연결 작업 부재는 ‘연결 작업 미입력’으로 보입니다. 로그 수·토큰·실행 시간은 생산성 순위로 사용하지 않습니다. raw ID·환경 ID·event 수는 출처 확인에만 둡니다.

## 막힘을 클릭한 뒤 읽어야 할 화면

상세는 별도 주소이며 제목만 봐도 선택한 프로젝트/단계/작업을 알 수 있어야 합니다. 분석 로그 나열 대신 다음 네 문장을 읽게 합니다.

```text
← Recall 전체 계획 / 데이터 연결
내부 API 연결 — 권한 확인 필요

왜 멈췄나요?  선언된 API 접근 권한이 없어 현재 연결 검사를 실행할 수 없습니다.
누가 맡나요?  작업 담당 Alice · 권한 확인 담당 미지정
지금 할 일    API 관리 담당자에게 접근 범위를 확인한 뒤 연결 검사를 다시 실행하세요.
완료 조건    현재 계획 버전의 연결 검사 통과와 결과 확인이 필요합니다.

참고한 도구   내부 API · 호출 실패 관측   [호출 근거]
이 판단의 근거 보기 ▸
```

‘완료 조건’은 기간이나 ETA 대신 충족해야 하는 기준을 설명합니다. 담당/다음 행동이 입력돼 있지 않으면 화면이 보완하지 않고 ‘담당 미지정’, ‘다음 행동 미기록’이라고 표시합니다. 권한 승인 기능이 없으면 승인 버튼을 만들지 않습니다. 실제 실패 사유를 자연어로 요약할 때도 의미를 확장하지 않습니다.

## 근거는 질문에서 찾아간다

기본 분석 근거 목록과 9개 분야 탭을 없애더라도 기록과 접근 경로는 보존합니다. 선택한 작업/세션/목표의 근거만 한 화면에서 읽고, 출처 펼침과 원본 링크로 이어집니다. 기존 `view=evidence` 주소는 삭제하지 않고 호환 경로로 유지하며 새 근거 개요로 연결합니다. 잘못된 주소와 근거 누락은 명시적으로 표시합니다.

| 사람의 질문 | 시작 위치 | 선택한 근거 화면에서 먼저 보여줄 것 | 원본 탐색 |
|---|---|---|---|
| 왜 막혔나요? | 막힌 작업 행 → 상세 → 근거 | 해당 요청/실패, 현재 계획·산출물 버전, 실제 담당·다음 행동 | 연결 검사/요청의 source_ref |
| 왜 완료라고 하나요? | 작업·Phase·최종 완료 상태 → 근거 | 그 범위의 완료 조건과 현재 유효 검사/인수, 남은 조건 | 검사 실행·문서 발췌 |
| 이 도구를 실제 썼나요? | Phase 참조 → 해당 API/MCP | 설정 선언/호출 관측/결과 참조 구분, 관련 세션 | 해당 도구 이벤트 |
| 이 세션은 무엇을 끝냈나요? | 사람 → 세션 → 선택 세션 | 시작 목표, 연결 작업, 종료 상태, 목표 검증/인수 | 세션의 명시적 출처 |
| 누가 무엇을 맡나요? | 공동 프로젝트 참여자 → 담당 작업 | 같은 프로젝트 안의 해당 사람 책임, 위임 기록 | assignment/작업 원문 |
| 왜 계획이 달라졌나요? | 현재 계획의 변경 표시 → 변경 근거 | 이전/현재 버전·변경 범위·이유·확인자 | 변경 기록/문서 |
| 회사·팀에 무엇을 기여했나요? | 회사·팀 목표 → 연결 프로젝트 | 지표 정의/기준/목표/기간/관측값, 기여 제안/확인 구분 | metric observation/확인 기록 |
| 무엇을 개선해야 하나요? | 판단 항목에 실제 분석 결과가 있을 때 | 근거·제안·처리 상태·만료 조건 | 해당 분석 기록·원본 |

두 번 클릭한 뒤 필요한 답을 얻는 것이 목표입니다. 예를 들어 프로젝트에서 ‘막힌 작업 행’ 1회, 상세의 ‘이 판단의 근거’ 1회로 현재 실패 근거를 읽어야 합니다. 거기서 원본을 펼치는 행동은 독자가 선택합니다. 어떤 분야 탭에 기록이 있는지 미리 알 필요가 없어야 합니다. 상세에서 전체 프로젝트의 무관한 로그를 검색하게 하면 실패입니다.

현재 데이터에 분석 결과·처리 기능이 없다면 ‘개선 제안’을 생성된 것처럼 보이지 않습니다. 9탭 제거가 새 AI 기능 도입 권한이나 신규 데이터 계약 변경 권한은 아닙니다.

## 회사·팀 목표 관리의 보존

기본 사람/프로젝트 흐름 옆에 ‘회사·팀 목표’ 진입점을 둡니다. 숨긴 `northStarArea`를 단순 복구해 기본 화면 아래 길게 붙이지 않습니다. 별도 화면에서 목표 한 개→연결된 프로젝트→확인된 기여를 읽습니다. 측정값이 없으면 ‘관측값 없음’으로 표시하며 테스트 통과·프로젝트 수·완료 단계 수로 지표를 채우지 않습니다. AI 제안과 사람 확인, 개인 목표의 미연결 상태를 보존합니다.

## 설계를 반박하는 사례와 통과 조건

| 반증 사례 | 잘못된 디자인 | 이 설계의 필수 결과 |
|---|---|---|
| Bob 선택 후 Alice의 막힘이 프로젝트 완료를 막음 | Alice 행을 숨겨 Bob 작업만 완료로 보임 | 공동 계획 전체와 Alice 막힘 유지, Bob 행만 강조 |
| 2단계와 3단계가 동시에 진행 | ‘현재 단계 2’라는 단일 포인터 | 두 행 모두 진행 중, 존재하는 의존성만 표현 |
| 세션 정상 종료·작업 검사 실패 | 세션 종료를 체크 완료로 표시 | 종료됨 / 목표 미달성 별도 표시 |
| 문서상 완료·현재 검사 없음 | 녹색 달성 상태 | 문서상 완료 / 현재 검증 미확인 |
| 예전 revision 검사 pass | 완료 막대 유지 | 현재 계산이 재검증 필요면 그대로 표시 |
| 날짜 없음 | 오늘 기준 ETA 또는 기간 막대 | 단계축 표시, 납기/기간 추정 없음 |
| 담당·다음 행동 없는 막힘 | AI가 담당과 해결책을 채움 | 미지정/미기록, 보완이 필요함을 표시 |
| 동일 목표 문구·다른 프로젝트 ID | 자동 합침 | 별개 유지, 실제 분석이 있을 때만 후보 제안 |
| 계획 15개 Phase·긴 작업명 | 카드 15개 세로 나열 | 동일 WBS 문법, 모든 Phase 접근, 펼침/줄바꿈 정렬 유지 |
| MCP 설정만 기록 | ‘사용한 MCP’ 확정 | 설정 선언으로 표시 |
| 업데이트 중 근거 읽는 중 | disclosure/focus/스크롤 초기화 | 선택 주소·초점·펼침·표 위치 유지 |
| 회사 지표 관측 없음 | 개발 완료율을 사업 기여로 사용 | 관측값 없음, 확인된 기여 링크만 표시 |

실제 데스크톱 검증에서는 최소 1280/1440px에서 처음 방문한 독자가 프로젝트 목표, 완료/현재/남음, 공동 담당을 설명할 수 있는지 관찰합니다. 막힘 클릭→정확한 상세→현재 근거→뒤로/새로고침 복귀를 실행합니다. 긴 문구와 많은 Phase 사례의 줄바꿈·행 정렬·스크롤, 키보드 진입·focus, 색 외 상태 구분을 확인합니다. 정적 DOM 검사나 새 runtime 테스트만으로 이 인수를 PASS하지 않습니다.

## 지금 실행 가능한 범위

기존 데이터·판정·계약을 유지하는 로컬 프런트엔드 개선으로 좁힙니다. WBS 기본 표시, 공동 책임 요약, 원자 작업 목록, 세션 단일 투영, 질문별 근거 IA, 회사·팀 진입점은 기존 자료로 가능한 후보입니다. 읽기 전용 데모와 비공개 실제 프로젝트에서 모두 데이터 출처를 구분합니다.

실행 전 부모가 결정할 항목은 두 가지입니다. 첫째, 날짜 없는 단계축의 단위가 Phase 순서임을 고정할 것. 둘째, 새 기본 화면에서 필수 질문별 근거 연결을 빠짐없이 보존할 것. 신규 API/DB/외부 모델 호출, 중앙 운영 변경, 배포/인프라 실행은 이번 설계 문서의 승인이 아닙니다. 로컬 UI 구현과 검증을 마친 뒤 현재 세션의 별도 권한 경계를 적용합니다.

Handoff 권장 패킷은 계획표/공동 책임, 사람 세션/회사 목표, 질문별 상세 근거의 세 단위입니다. 동일 파일의 함수 override가 얽혀 있으므로 병렬 수정 시 파일 소유권을 먼저 나누거나 순차 반영해야 합니다. 부모가 최종 통합 화면의 목적·데스크톱 시각 인수를 맡습니다. 분석 문서를 작성한 사실은 이 패킷들의 구현 완료가 아닙니다.

## Astra 교차검토 전달 의견과 합의

부모가 전달한 Astra 검토도 기본 WBS 숨김, Phase `replaceChildren`로 작업 진입로 삭제, label 없는 미니 막대를 근본 원인으로 확인했습니다. 다음은 교차검토를 반영한 구현 기준입니다. Astra 원문을 직접 열어 확인한 기록은 아니며 부모의 전달 내용을 기준으로 반영했습니다.

- 목록은 간결한 프로젝트 행, 기본 계획은 계층형 WBS와 검사 gate, 상세는 선택 대상 하나라는 세 화면 문법으로 통일합니다.
- 계획 화면에서 ‘완료한 작업’과 ‘현재 검사를 통과한 단계’를 구별합니다. 작업이 끝나도 Phase gate가 남으면 해당 Phase는 완료로 표시하지 않습니다. 최종 gate는 모든 Phase와 별도의 완료 조건으로 유지합니다.
- 현재 진행하는 행과 아직 시작하지 않은 행을 단어·기호로 구분하고, 여러 현재 작업을 허용합니다. 사람 필터는 공동 전체 계획을 유지하며 해당 책임만 강조합니다.
- 질문별 근거 화면을 기본으로 사용하고 기술 원문은 별도 펼침/원본 링크에 보존합니다. 세션은 actor/environment/source/session 식별로 겹치지 않는 실행 이력을 한 번만 표시합니다. 생명주기 종료와 목표 완료는 별도입니다.
- 출처가 없어 계산할 수 없는 개수는 0으로 만들지 않습니다. ‘계획 미입력’, ‘세션 기록 미관측’, ‘현재 검증 미확인’을 대상별로 정확히 쓰며 일괄 unknown으로 섞지 않습니다. 기록을 관측했고 해당 항목이 실제로 없을 때만 0건이라고 표시합니다.
- 명시적 schedule만 날짜축으로 사용하고, 없으면 단계축을 사용합니다. 가상 샘플 일정과 실제 일정의 출처를 같은 상태로 취급하지 않습니다.

교차검토의 구조 합의는 실제 데스크톱 가독성 PASS가 아닙니다. 이번 구현 후 현재 화면을 직접 관찰해 인수해야 합니다.
